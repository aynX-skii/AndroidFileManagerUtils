# FileBridge 传输协议规范

本文档是**两端实现的唯一依据**，分两部分：

| | 内容 | 状态 |
|---|---|---|
| **第一部分** | v1：线格式、接口清单、服务端规则 | 稳定，是兼容基线 |
| **第二部分** | v2：加密与身份（双向 TLS + 配对） | 见那一部分开头的实现状态表 |

v2 **没有改动任何 `/api/*` 的线格式** —— 它改的是"凭什么信这条连接"。
所以第一部分照旧有效，读实现时两部分都要看。
引用时写 `§3.4`（第一部分）或 `v2 §5.2`（第二部分）。

---

# 第一部分：v1 —— 线格式与接口

所有内容都与两端现有实现严格对应，括号中标注了对应的源码位置。

传输层只用两样东西：

| 用途 | 协议 | 默认端口 |
|------|------|----------|
| 设备发现 | UDP 广播 | 8766 |
| 文件传输 | HTTP/1.1（v2 起可套 TLS） | 8765 |

设计原则：**协议是对称的**。手机和 PC 实现的是同一套接口，谁当服务端由场景决定
（手机收文件 → 手机当服务端；手机推文件到 PC → PC 当服务端）。因此 Linux 端最终
要实现两半：客户端（`ls` / `get` / `put`）和服务端（`serve`）。

### 常量的唯一真源

本文档里出现的所有**两端必须一致**的数值（端口、超时、冷却时长、退避参数、
券的 TTL 与截断长度……）都在 [`constants.json`](constants.json) 里，
由 [`tools/gen_constants.py`](../tools/gen_constants.py) 生成两端的常量文件：

```bash
python3 tools/gen_constants.py          # 重新生成
python3 tools/gen_constants.py --check  # 只比对，漂了就退出 1
```

生成结果（`ProtocolConstants.kt` / `ProtocolConstants.h`）**两个仓库都提交**，
所以各自单独 clone 也能构建，不需要另一个仓库在场。它们带 DO-NOT-EDIT 头，
改值请改 `constants.json` 再重新生成。

> 这些常量以前是靠注释互指来同步的——"两边必须一致，否则…"写了四五处。
> 问题在于不一致的表现是"同一个网络里两台设备行为不同"，
> 排查时第一反应会是网络问题，根本不会想到常量。
>
> 纯本地的调优值（缓冲区大小、写入水位线）**不在**这里：它们本来就该各调各的。

## 1. 设备发现（UDP 8766）

### 1.1 探测包

客户端向所有接口的广播地址发送一个 UDP 包，载荷为纯文本：

```
AFMU-DISCOVER/1\n
```

接收端只检查**前缀** `AFMU-DISCOVER`（[Discovery.kt:PROBE_PREFIX](../app/src/main/java/com/aynux/afmu/core/Discovery.kt)），
后面的版本号目前被忽略，可用于以后扩展。

广播地址来源：遍历所有 up 且非 loopback 的接口，取其 broadcast 地址；再追加
`255.255.255.255` 作为兜底。Linux 下可用 `ioctl(SIOCGIFBRDADDR = 0x8919)` 获取，
无需第三方库。

### 1.2 应答包

每个在线设备回一个 UDP 包，载荷是单行 JSON。**常态下只有两个字段**：

```json
{"afmu": 1, "port": 8765}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `afmu` | int | 是 | 协议版本，当前恒为 `1`。字段缺失 → 判定为非本协议设备，丢弃 |
| `port` | int | 是 | **实际** HTTP 端口，不一定是 8765，见 §2.1 |
| `name` | string | 否 | 设备显示名。**只在配对模式下出现**，见 §1.5 |
| `os` | string | 否 | `android` 或 `linux`。**只在配对模式下出现**，见 §1.5 |

**应答里绝不包含 token。** 发现是公开的，鉴权是另一回事。

**客户端必须容忍 `name` / `os` 缺失**，退回显示 `host:port` 即可，不要当成错误。

### 1.3 实现要点

- 应答用 `sendto()` 直接回到探测包的源地址和源端口，不要回广播。
- 服务端 socket 必须设置 `SO_REUSEADDR`，否则重启时 8766 会被 TIME_WAIT 占住。
- 客户端应过滤掉**自己**的 IP：如果本机也在监听 8766，广播会把自己的应答也收回来
  （Android 端就是这么处理的）。
- App 内可关闭"可被发现"开关；关闭后收到探测包直接忽略，不应答。
- 收集应答时按 `host:port` 去重，同一台设备多网卡会答多次。
- 建议超时 1.0–2.0 秒，采用"边收边等"而非固定 sleep。

### 1.4 定向探测

广播被 AP 隔离拦截时，可以对已知 IP 单播同样的探测包（Android 端的
`Discovery.probeHost()`）。收到应答即可确认对方端口和名字，无需用户输入端口。

### 1.5 配对模式

v1 早期的应答长这样：

```json
{"afmu": 1, "name": "icelab", "os": "linux", "port": 8765}
```

往 UDP 8766 发一个包，局域网里**任何人**都能拿到"这台机器叫 icelab、跑 Linux"。
这是一次不需要任何凭证的信息泄露，而且发生在用户完全不知情的时候——
设备名往往就是人名或工位名。

于是分成两种模式：

| 模式 | 应答 | 何时 |
|------|------|------|
| **常态**（默认） | `{"afmu":1,"port":8765}` | 一直 |
| **配对模式** | 加上 `name` 和 `os` | 用户在界面上显式点击后的 **60 秒** |

超时自动回到常态。**"陌生人能看到设备名"的窗口就从"永远"缩短成
"用户主动开启的那一分钟"。**

这和"可被发现"开关是两个正交的东西，别混淆：

- `discoverable = false` → **完全不应答**（原有开关，不变）
- `discoverable = true`，非配对模式 → 应答，但只有 `afmu` 和 `port`
- `discoverable = true`，配对模式 → 应答完整信息，限时 60 秒

#### 客户端：记住见过的名字

常态应答没有名字，直接显示会让设备列表变成一片 `192.168.1.x:8765`。
所以客户端**应该按 `host:port` 缓存见过的 `name` / `os`**：
已经认识的设备照样显示名字，只有素未谋面的才是一串地址——泄露没了，熟悉感还在。

DHCP 换地址后缓存会失效，那时退回显示地址，不是错误。

> 这也是 v2 §6 的前置工作。v2 用滚动 `rid` 让已配对设备**在协议层**认出对方，
> 那时这份本地缓存就可以退役。

## 2. HTTP 接口（TCP 8765）

### 2.1 端口选择

服务端依次尝试绑定 `8765`、`8766`、`8767`，全失败则绑定随机空闲端口
（[HttpServer.kt `bind()`](../app/src/main/java/com/aynux/afmu/core/HttpServer.kt)）。

> **因此客户端不能硬编码 8765**，必须以发现应答里的 `port` 为准；
> 只有用户手动输入地址时才回退到默认值。

### 2.2 鉴权

除 `GET /` 外，所有 `/api/*` 请求都必须带 token。两种等价写法，按此顺序取第一个非空值：

1. `X-AFMU-Token: <token>` ← **推荐**
2. `Authorization: Bearer <token>`

> **`?token=` 已移除。** 凭证进了 URL 就会落进代理日志、浏览器历史和 `Referer`，
> 而且 `<img src="…?token=…">` 这种不带 `Origin` 的 GET 正好绕过 §2.4 的跨站防护。
> 服务端**必须**拒绝查询参数里的 token（当作没带，回 `401`）。
> 它当初存在的唯一理由——浏览器 `<a href>` 带不了自定义头——由 §2.5 的下载券承担。

token 是 10 位小写字母数字（去掉了 `i l o 0 1` 等易混字符），由手机生成、显示在 App 首页，
用户手抄到 PC。比较使用常数时间算法。

失败返回：

```
HTTP/1.1 401 Unauthorized
Content-Type: application/json; charset=utf-8

{"ok": false, "error": "invalid or missing token"}
```

#### 失败退避（服务端必须实现）

token 有约 49 bit 熵，够用——**但前提是猜错要付出代价**。
没有这一层时，同一个地址连打 200 次错误 token 只花 0.78 秒且毫无惩罚，
爆破成本只剩带宽。

按**来源 IP** 计数，参数两端必须一致：

| 项 | 值 | 理由 |
|------|------|------|
| 宽限次数 | 前 `5` 次失败不惩罚 | token 是手抄的，打错很正常 |
| 退避时长 | 第 `5+n` 次失败后封 `min(2ⁿ⁻¹, 60)` 秒 | 1, 2, 4, 8, 16, 32, 60, 60… |
| 遗忘窗口 | `15` 分钟内没有新的失败就清零 | 别让一次误操作留一整天 |
| 成功即清零 | 任何一次校验通过都删掉该地址的记录 | 只惩罚**连续**失败；猜不中的人永远清不了零 |

封禁期内的 `/api/*`：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 8
Content-Type: application/json; charset=utf-8

{"ok": false, "error": "too many failed attempts, retry in 8s"}
```

两条实现要求：

- **封禁期内不要比对 token**，直接回 429。比对本身是常数时间的，
  但「有没有走到比对」是可观测的，挡在门外最干净。
- **惩罚必须是立即回 429，不能是 sleep。** 占住线程正是攻击者想要的，
  而 Linux 端跑在单个事件循环里，睡一下等于全站停摆。

客户端要把 `429` 和 `401` 区别对待：`401` 是「token 不对，去改配置」，
`429` 是「等 `Retry-After` 秒再来，token 可能是对的」。

> 协议是明文 HTTP，token 只防同一局域网内的误连和顺手翻看，**不是**对抗嗅探的安全边界。
> 不要在不可信网络（公共 Wi-Fi、咖啡厅）上开启服务。

### 2.3 通用约定

- **HTTP/1.1**，必须发 `Content-Length`（不支持无长度的响应体）。
- 成功响应体统一含 `"ok": true`；失败统一为 `{"ok": false, "error": "<人类可读原因>"}`。
  客户端应先看 `ok` 再看 HTTP 状态码。
- 所有路径参数是**目标设备上的绝对文件系统路径**（如 `/storage/emulated/0/DCIM`），
  经过 URL 编码。空字符串或 `/` 是特殊值，表示"根列表"，见 §3.2。
- `+` 不被解释为空格；空格必须编码为 `%20`。
- 响应带 `Cache-Control: no-store`。
- 带请求体的请求，服务端处理完后会发 `Connection: close`（避免流位置错乱），
  客户端不要指望在上传后复用连接。GET 请求支持 keep-alive。
- **拒绝一个还没读请求体的请求时，也必须发 `Connection: close`**（401 / 403 / 405 等）。
  否则剩下的请求体会被当成流水线里的下一个请求解析出一堆乱七八糟的 400。
  服务端如果选择把请求体读完丢弃（drain）再复用连接，则要给丢弃量设上限。
- 服务端 socket 超时 120 秒；长时间无数据的连接会被断开。

### 2.4 Host 白名单与 Origin 校验（服务端必须实现）

token 挡的是"没有凭证的人"。这一节挡的是另一类完全不同的攻击：
**让受害者自己的浏览器替攻击者发请求**——凭证是浏览器自动带上的，token 帮不上忙。

#### DNS rebinding

受害者打开攻击者的页面，页面请求 `http://evil.example.com:8765/`，
而那个域名被解析到 `192.168.1.42`（受害者的手机）。
同源策略帮不上忙——**源就是攻击者的域名**，所以页面能正常读到响应。

服务端唯一能分辨的地方是 `Host` 头：它写的是 `evil.example.com`，
而正常访问写的是 IP 或 `.local` 名字。于是规则只看形态：

> **`Host` 的主机名必须是 IP 字面量、`localhost`、或 `.local` 结尾。**
> 否则 `403` `{"ok":false,"error":"host not allowed"}`。

不要去枚举本机地址（多网卡 / DHCP 下会漂，还容易漏），也不需要——
DNS rebinding 的前提就是用一个 DNS 名字，上面三种形态都不是。

IPv4 的判定要**严格**：只接受四段十进制、每段 0–255。
`1.2.3`、`0x7f.0.0.1`、`2130706433` 这类宽松写法一律拒——
宽松的解析器正是 rebinding 想要的。

#### 跨站请求

挡住 DNS 名字之后，攻击者页面还能直接写 `http://192.168.1.42:8765/api/…`。
这时浏览器会带上 `Origin`：

> **`Origin` 缺失 → 放行**（原生客户端不发它）。
> **`Origin` 存在 → 主机名和端口都必须和 `Host` 一致**，否则 `403`
> `{"ok":false,"error":"cross-origin request refused"}`。

两个容易写错的点：

- **端口必须一起比。** 只比主机名的话，同一台设备上任何别的 HTTP 服务
  （比如 `:9999` 上的一个页面）都能驱动本机的 API。
  两边的端口都可能是隐含的，补齐之后再比。
- `Origin: null`（浏览器在不透明源里发的）**要拒**，那不是本机。

#### 检查位置

**排在所有路由之前，包括 `GET /`**——浏览器界面正是这类攻击的入口，
不能只保护 `/api/*`。也要排在 token 检查之前：这两条和有没有凭证无关。

> 这一层和 `?token=` 是互相咬合的：只要凭证还能出现在 URL 里，
> 攻击者页面用一个 `<img src="…?token=…">` 就能发出不带 `Origin` 的 GET。
> 两个一起做才完整。

### 2.5 下载券

浏览器的 `<a href>` 带不了自定义头。这是 `?token=` 当初存在的唯一理由，
去掉它之后需要一个替代物。

```
GET /api/download?path=…&ticket=<exp>.<mac>

exp = 过期时刻的 Unix 秒（十进制）
mac = base64url( HMAC-SHA256( token, "afmu-dl-v1\n" || exp || "\n" || path ) ) 取前 22 字符
```

- **防伪造**：MAC 用本机 token 当密钥，服务端**无状态**校验，不记任何已签发的券。
  域分隔前缀 `afmu-dl-v1\n` 保证这个 MAC 不会被当成同一把钥匙算出来的别的用途的 MAC；
  两个换行保证 `exp` 和 `path` 不会黏成有歧义的串。
- **绑定路径**：换个 `path` 券就失效，所以一张券只能打开一个文件。
- **过期语义**：`exp` 约束的是**开始**下载。服务端在决定响应之前校验一次，
  一旦开始写响应体就不再看——否则 10 秒过期等于禁止下载任何大文件。
- 22 个 base64url 字符 = 132 bit，10 秒窗口内爆破无从谈起。

> **它不是"一次性"的。** 真一次性要服务端存一张已用 nonce 表，
> 而那和上面的无状态校验直接矛盾。在它活着的那几秒里券可以被重放——
> 但只能重放**同一个路径的下载**，所以这笔交换划算。
> **别在界面或文档里叫它一次性。**

#### `GET /api/ticket` — 签一张券

| 参数 | 必填 | 说明 |
|------|------|------|
| `path` | 是 | 文件绝对路径 |

需要**头**鉴权（`X-AFMU-Token` 或 `Bearer`），不接受券——券不能用来签新券。

```json
{"ok": true, "ticket": "1786000123.9XFHTB4NRW2PLDS8VCGYM3", "expires": 10}
```

失败：`404` 路径不存在、不是文件或越界。

> **先解析路径再签券。** 给一个越界的路径签券，等于向对方确认了它存在。

#### 实现要点

- 只有 `/api/download` 认券，别的接口一律只认头。
- 券是**补充**不是替代：原生客户端继续用头，根本不碰这一套。
- 浏览器界面**不能自己算 MAC**：`crypto.subtle` 在明文 HTTP 下不可用
  （非安全上下文）。所以必须由服务端签发，页面在**点击时**才去要一张——
  渲染列表时就要会让一个 500 个文件的目录发出 500 个没人需要的请求。

## 3. 接口清单

### 3.1 `GET /api/info` — 设备信息

```json
{
  "ok": true,
  "name": "Pixel 8",
  "os": "android",
  "androidRelease": "15",
  "sdk": 35,
  "protocol": 1,
  "writable": true,
  "fullStorageAccess": true,
  "inbox": "/storage/emulated/0/Download/FileBridge",
  "roots": [
    {"name": "Internal storage", "path": "/storage/emulated/0"},
    {"name": "App folder (always writable)", "path": "/storage/emulated/0/Android/data/com.aynux.afmu/files"}
  ]
}
```

| 字段 | 说明 |
|------|------|
| `writable` | 为 `false` 时 upload / mkdir / delete 一律返回 403 |
| `fullStorageAccess` | Android 特有。为 `false` 时 `roots` 只有 App 私有目录 |
| `inbox` | 未指定 `dir` 的上传落到哪里 |
| `roots` | 可浏览的根目录列表，等价于 `GET /api/list?path=/` 的结果 |

Linux 服务端应至少返回 `ok` / `name` / `os` / `protocol` / `writable` / `inbox` / `roots`；
`fullStorageAccess`、`sdk` 等 Android 专有字段可省略，客户端必须容忍缺失。

### 3.2 `GET /api/list` — 列目录

| 参数 | 必填 | 说明 |
|------|------|------|
| `path` | 否 | 绝对路径。**省略或传 `/` 时返回根目录列表** |

```json
{
  "ok": true,
  "path": "/storage/emulated/0/DCIM",
  "parent": "/storage/emulated/0",
  "entries": [
    {"name": "Camera", "path": "/storage/emulated/0/DCIM/Camera", "dir": true,  "size": 0,      "mtime": 1754400000},
    {"name": "a.jpg",  "path": "/storage/emulated/0/DCIM/a.jpg",  "dir": false, "size": 238411, "mtime": 1754399000}
  ]
}
```

- `parent`：根列表时为 `null`；当父目录已在允许范围外时为 `"/"`（即回到根列表）。
- `mtime`：**Unix 秒**（不是毫秒）。
- `size`：目录恒为 `0`。
- 排序：目录在前，然后按文件名小写升序。
- 路径不存在 / 不是目录 / 越界 → `404` + `{"ok":false,...}`。

### 3.3 `GET|HEAD /api/download` — 下载

| 参数 | 必填 | 说明 |
|------|------|------|
| `path` | 是 | 文件绝对路径 |

响应头：

```
Content-Type: <按扩展名推断，未知为 application/octet-stream>
Content-Length: <字节数>
Accept-Ranges: bytes
Content-Disposition: attachment; filename="a.jpg"; filename*=UTF-8''a.jpg
Last-Modified: <RFC 1123 GMT>
```

**断点续传**：支持 `Range: bytes=<start>-[<end>]` 和 `Range: bytes=-<suffix>`。

- 命中 → `206 Partial Content` + `Content-Range: bytes <start>-<end>/<total>`
- 越界 → `416 Range Not Satisfiable` + `Content-Range: bytes */<total>`，无响应体
- 只支持**单区间**；多区间请求只取第一段

`HEAD` 返回完全相同的头、无响应体，可用来取大小和校验存在性。

文件名解析优先用 `filename*=UTF-8''<pct-encoded>`（中文文件名走这条），
回退到 `filename="..."`。

### 3.4 `POST|PUT /api/upload` — 上传

| 参数 | 必填 | 说明 |
|------|------|------|
| `name` | 原始体时必填 | 目标文件名；会被服务端做安全化处理（§4.2） |
| `dir` | 否 | 目标目录绝对路径。**省略、越界或不可写时落到 `inbox`** |
| `overwrite` | 否 | `1` = 覆盖同名文件；否则自动改名为 `a (1).txt` |

支持两种请求体：

**A. 原始字节流（客户端首选）**

```
POST /api/upload?name=clip.mp4&dir=%2Fstorage%2Femulated%2F0%2FMovies HTTP/1.1
X-AFMU-Token: abc123xyz9
Content-Type: application/octet-stream
Content-Length: 734003200

<raw bytes>
```

也接受 `Transfer-Encoding: chunked`（大小未知时用，例如从管道读）。
二者必居其一，都没有 → 500。

**B. `multipart/form-data`**（浏览器表单、`curl -F` 用）

服务端流式解析，逐段直接落盘，不在内存里缓冲整个文件。带 `filename` 的段才会被保存，
普通表单字段被丢弃。单次请求可含多个文件。

**响应（两种体一致）**

```json
{"ok": true, "saved": ["/storage/emulated/0/Movies/clip.mp4"]}
```

`saved` 是实际落盘路径数组（改名/落到 inbox 后的真实结果）。
Android 走 MediaStore 兜底时，这里是相对路径 `Download/FileBridge/clip.mp4`。

**`ok: true` 必须意味着文件真的完整落盘了。** 两个必须挡住的情况：

- multipart 的 `Content-Length` 用完了但结尾边界 `--<boundary>--` 没到 → 请求体被截断，
  回 `400` 并删掉 `.afmu-part`；
- 一个文件段都没解析出来 → 回 `400`，不要回 `{"ok":true,"saved":[]}`。

客户端拿到空的 `saved` 时通常会回退成"用原文件名显示成功"，于是文件静默丢失、
用户毫不知情——这是最坏的一种失败方式。

**服务端只有在对端半关闭（FIN）时才可能察觉截断。** 光是"发的字节数少于
`Content-Length`"察觉不到——那和"对端还没发完"没有区别，只能等 socket 超时。
所以这里的要求分两层：

| 层次 | 要求 | 说明 |
|------|------|------|
| **硬不变量** | 绝不回 `ok: true`，绝不留下 `.afmu-part` 或半个正式文件 | 两端实现都必须做到，没有例外 |
| **期望行为** | 回 `400` | 客户端据此区分"服务端拒绝了"和"网线被拔了" |

**已知偏差（Linux / Qt）**：`400` 发不出去，客户端收到的是连接中断。
硬不变量仍然守住——残片会删，绝不会回 `ok:true`。

原因查清了，别再重试同一条路：

- 挂 `QTcpSocket::readChannelFinished` 是唯一看似可行的时机，**信号确实会触发**，
  此时连接阶段也确实还是「正在收请求体」；
- 但那一刻 `socket->state()` 已经是 `UnconnectedState`——
  **Qt 在发出该信号之前就把连接拆掉了**，写进去的字节被直接丢弃。
  实测验证过，不是推测。
- `QTcpSocket` 不支持 TCP 半关闭。要修就得把整个连接层从 `QTcpSocket`
  换成 `QSocketNotifier` + 裸 fd 自己管读写两个方向。

对一个只提升诊断信息质量的点来说，这个代价不成比例，所以**接受这个偏差**。
一致性测试里它被标为「已知偏差」，不计入失败。

> 因此：**客户端必须把"响应到达之前连接断开"一律当作失败处理**，
> 这条不是可选的容错，是协议要求——Linux 端在这种情况下就是不会给你状态码。

失败：`400` 请求体截断或没有文件段、`403` 只读、`405` 方法不对、`500` 写入失败。

### 3.5 `POST /api/mkdir` — 建目录

| 参数 | 必填 | 说明 |
|------|------|------|
| `path` | 是 | 父目录绝对路径 |
| `name` | 是 | 新目录名，会被安全化 |

→ `{"ok": true, "path": "/storage/emulated/0/DCIM/新建"}`

**必填参数缺失 → `400`，不是 `404`。** 两个检查的顺序不能颠倒：
`path` 缺失时路径解析同样得到空结果，先解析就会把「没传参数」误报成「目录不存在」。
先判参数是否为空（`400`），再解析路径、判目标是否存在且在 root 之下（`404`）。

失败：`400` 缺 `path` 或 `name`、`403` 只读、`404` 父目录不存在或越界、`405` 方法不对、`500` 创建失败。

### 3.6 `POST /api/delete` — 删除

| 参数 | 必填 | 说明 |
|------|------|------|
| `path` | 是 | 目标绝对路径 |
| `recursive` | 目录时必填 | `1` 才允许删非空目录 |

→ `{"ok": true}`

**根目录本身不允许删**：`path` 恰好等于某个 root 时返回 `403`
`{"ok":false,"error":"refusing to delete a shared root"}`。root 代表整个存储卷／共享目录，
`recursive=1` 删它是一次不可逆的灾难，而且从来不是用户的本意。root **里面**的
单个文件和子目录仍然正常可删。

> 删除是不可逆的，且**没有回收站**。客户端必须在 UI 上做二次确认
> （CLI 则要求显式 `--yes`）。

### 3.7 `GET /` — 浏览器界面

Android 端返回一个自包含的单页 HTML（无外链资源），PC 上没装任何东西时可直接
浏览器访问 `http://<手机IP>:<port>` 完成收发。

Linux 服务端**不需要**实现这个页面，返回一句纯文本说明即可。

### 3.8 `POST|GET /api/authorize` — 授权连接（**不需要 token**）

给「客户端手上还没有对端 token」这一种情况用：客户端发起请求，对端在自己屏幕上弹窗，
用户点「允许」之后 token 才交出去。手抄 token 的老路子完全保留，两者并存。

> **这是整套协议里唯一免鉴权的 `/api/*` 接口**，因为它存在的意义就是「还没有 token」。
> 于是它必须自己扛住滥用，下面的约束不是建议，是实现要求。

**`POST /api/authorize`** — 登记一个请求

| 参数 | 必填 | 说明 |
|------|------|------|
| `name` | 否 | 请求方设备名，显示在弹窗里 |
| `os` | 否 | `linux` / `android` |
| `code` | 是 | 4 位确认码，**请求方生成并显示在自己屏幕上** |
| `port` | 否 | 请求方自己的服务端口，供接收方回连 |

```json
{"ok": true, "request": "3f9c…（32 位十六进制）", "expires": 60}
```

- `request` 是**只发给请求方的一次性密钥**，取结果时凭它认人；不要写日志、不要广播。
- `code` 由请求方生成、两端同时显示。同一局域网里谁都能让对方弹窗，用户唯一能分辨
  「弹的是不是我刚点的那一下」的手段就是比对这四位。接收方必须原样显示，不要自己再生成。
- 请求方地址取 socket 的对端 IP，**不信任任何请求参数里的 host**。

失败：

| 状态码 | 含义 |
|--------|------|
| `403` | 接收方关掉了「允许连接请求」开关 |
| `429` | 已经有一个请求在等待，或该地址刚被拒绝过（冷却中） |

**`GET /api/authorize?request=<id>`** — 轮询结果

```json
{"ok": true, "status": "pending"}
{"ok": true, "status": "granted", "token": "abc123xyz9", "name": "Pixel 8", "port": 8765}
{"ok": true, "status": "denied"}
{"ok": true, "status": "expired"}
```

`id` 不认识（从没见过，或结果已过保留期）→ `404`。客户端应把 `404` 当作 `expired` 处理。

建议轮询间隔 1 秒，GET 支持 keep-alive，所以整个等待过程复用同一条连接。

**接收方必须做到的几件事**（缺一条这个接口就变成骚扰入口）：

- 同一时刻只保留**一个**待决请求，新的一律 `429`；
- 超时（`kAuthTimeoutSec` = 60 秒）默认视为拒绝，不是允许；
- 提供一个可以彻底关掉这个接口的开关；
- 服务端停止时清空所有待决请求——没人能再来取结果了；
- 按下面的表做**冷却**。

#### 冷却与升级

只有"同一时刻一个待决请求"是不够的：拒绝、等一分钟、再来，可以一直弹下去；
而局域网里换个源地址是零成本的事，纯按地址算的限制根本挡不住。
所以有两层，参数两端必须一致：

| 触发 | 冷却对象 | 时长 |
|------|---------|------|
| 用户点「拒绝」 | **该地址** | `60s × 2^(该地址被拒次数-1)`，封顶 30 分钟 |
| 请求超时未决 | **该地址** | 固定 `60s`，**不**参与上面的升级计数 |
| 上面任意一种 | **所有地址**（全局） | `10s × 2^(连续拒绝数-1)`，封顶 5 分钟 |
| 用户点「允许」 | —— | 清空该地址的计数**和**全局计数 |
| 30 分钟无新拒绝 | —— | 升级计数归零 |

- **全局冷却是唯一能挡住换 IP 刷屏的东西**，别省。它不看是谁在请求。
- 超时算"软拒绝"：对方确实没做错什么（是用户没来得及看），所以不升级，
  但仍要冷却——否则"发一个然后挂机等超时"照样能一分钟弹一次。
- 用户点「允许」必须清账。否则用户先拒了一次、随后想起来要配对，
  第二次会被自己刚才那次拒绝的冷却挡在门外。

冷却导致的 `429` 要带 `Retry-After`：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 40

{"ok": false, "error": "another request is pending, or this address was refused recently"}
```

**「已有一个请求在等用户点」这种 `429` 不带 `Retry-After`**——那要等多久取决于用户，
报不出准确秒数就不要瞎报一个。

**接收方可以不实现这个接口**。没实现时的表现有两种，客户端都要当成「对端不支持」而不是
「请求失败」：`404`（没有这条路由），或者 `401`（把 `/api/*` 一律先过 token 检查，
于是免鉴权的请求也被挡下）。

**两端都实现了这个接口，也都会主动发起它**，因此 Linux ↔ Linux、Android ↔ Android
和两者混连走的是同一条路：谁没有对方的 token，谁就来敲门，另一边在自己屏幕上确认。
扫二维码（§5）仍然有效，是 PC 把 token 交出去的另一条路。

### 3.9 `POST /api/pair` — 回填对端信息

一次配对之后把**反方向**也配好：扫码方 / 被授权方拿到对端 token 之后，用这个接口把
自己的地址和 token 送回去，于是两个方向都不用再手抄。

| 参数 | 必填 | 说明 |
|------|------|------|
| `token` | 是 | **请求方自己的** token |
| `port` | 否 | 请求方的服务端口，默认 8765 |
| `name` | 否 | 请求方设备名 |
| `os` | 否 | `linux` / `android` |

需要 token（用的是**接收方的** token，请求方刚拿到的那个）。

```json
{"ok": true, "name": "ice-desktop", "os": "linux", "protocol": 1}
```

失败：`400` 没带 `token`、`401` token 不对、`405` 方法不对。

接收方存下 `token` 作为自己的「对端 token」，并把对方地址记成
`<socket 的对端 IP>:<port>`——同样**不信任参数里的 host**，否则这个接口就成了
「让 A 把 token 指向 C」的跳板。

## 4. 服务端必须遵守的规则

### 4.1 路径越界防护（最重要）

持有 token 的一方能指定任意路径字符串。服务端必须：

1. 把用户传入的路径 **canonicalize**（解析 `..`、符号链接），Kotlin 用
   `File.canonicalFile`，Python 用 `Path.resolve()`；
2. 检查结果是否等于某个 root，或位于某个 root **之下**；
3. 不满足 → 当作"不存在"返回 404，**不要**泄露真实原因。

对应实现：[Storage.kt `resolve()`](../app/src/main/java/com/aynux/afmu/core/Storage.kt)。

### 4.2 文件名安全化

对所有来自对端的文件名（`name` 参数、multipart 的 `filename`）：

- 剥掉路径部分（`/` 和 `\` 之后的最后一段）——防止 `../../etc/passwd`
- 把控制字符和 `< > : " | ? *` 替换为 `_`（兼容 FAT32/exFAT 的 SD 卡）
- 截断到 200 字符
- 结果为空、或恰好是 `.` / `..` → `unnamed`

> `.` 和 `..` 必须单独挡：剥路径部分对它们不起作用（里面没有 `/`），
> 而 `File(dir, "..")` 指向的是父目录，不是 `dir` 里的一个文件。

### 4.3 原子落盘

先写 `<目标名>.afmu-part`，完整收完后 `rename()` 到正式名。
传输中断时删掉 `.afmu-part`，**绝不留下半个文件冒充完整文件**。

续传时可以保留 `.afmu-part` 并用其大小作为 `Range` 起点。但**残片必须能追溯到它属于哪个
远端文件**：临时名只用文件名的话，两个不同目录下的同名文件、或上次失败遗留的残片，
会共用同一个 `.afmu-part`，续传起点就是错的，最后 `rename` 出一个静默损坏的文件。
可行做法是把远端路径的哈希拼进临时名，并在残片大小 ≥ 已知总大小时直接丢弃重来。

### 4.4 自动改名

`overwrite != 1` 且目标已存在时，按 `名字 (1).扩展名`、`名字 (2).扩展名` 递增，
上限 10000 次。

### 4.5 并发

每个连接一个线程即可（Android 端用 cached thread pool，Python 用
`ThreadingHTTPServer`）。单个请求出异常必须只断这一条连接，不能拖垮服务。

## 5. 配对二维码

PC 端显示、手机端扫描。一次扫码把地址、端口和 token 全给到，用户不用再手抄那 10 位。

载荷是一行纯 ASCII 文本（**不要**用 UTF-8 直出中文：那要靠 ECI 段声明字符集，
各家扫码器支持程度不一。设备名一律百分号编码）：

```
afmu://pair?v=1&host=192.168.1.30&hosts=192.168.1.30,10.42.0.1&port=8765&token=a7k2m9x4qp&name=ice-desktop&os=linux
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `v` | 否 | 协议版本，缺省按 1 处理。**大于自己支持的版本 → 拒绝，不要猜** |
| `host` | 是 | 首选地址 |
| `hosts` | 否 | 逗号分隔的全部候选地址，多网卡时给出 |
| `port` | 否 | 服务端口，缺省 8765 |
| `token` | 是 | **显示方自己的** token |
| `name` | 否 | 显示方设备名，百分号编码 |
| `os` | 否 | `linux` / `android` |

扫描方拿到之后：

1. 存下 `token` 作为「对端 token」；
2. 按 `host` → `hosts` 的顺序逐个 `GET /api/info`，**第一个应答的才是能用的那个**
   ——多网卡 PC 会广播好几个地址，只有和自己同网段的那个通；
3. 全都不通就报错，不要留下一个连不上的配置；
4. 连通之后 `POST /api/pair`（§3.9）把自己的 token 送回去，两个方向一次配好。

不是本协议的码（扫码器对着世界会解出各种条码）→ 直接忽略并提示，不要当成错误。

> 二维码里是明文 token，等价于把访问权交出去。截图、转发、投屏都要当成泄露处理。

## 6. 典型时序

### 6.1 PC 拉取手机上的文件

```
PC                                              手机
 |-- UDP  AFMU-DISCOVER/1  → 255.255.255.255:8766 |
 |← UDP  {"afmu":1,"name":"Pixel 8","port":8765} --|
 |                                                 |
 |-- GET /api/info            (X-AFMU-Token) ----→ |
 |← 200 {"ok":true,"roots":[...]}  ---------------|
 |-- GET /api/list?path=/storage/emulated/0/DCIM →|
 |← 200 {"entries":[...]}  -----------------------|
 |-- GET /api/download?path=...  (Range: bytes=0-)→|
 |← 206 <文件字节流>  ----------------------------|
```

### 6.2 手机推文件到 PC

角色互换：PC 侧运行服务端，手机侧用
[PeerClient.kt](../app/src/main/java/com/aynux/afmu/core/PeerClient.kt) 发起：

```
手机                                             PC
 |-- UDP  AFMU-DISCOVER/1 → 广播:8766 ----------→ |
 |← UDP  {"afmu":1,"os":"linux","port":8765} ----|
 |-- POST /api/upload?name=IMG_0001.jpg --------→ |
 |    Content-Length: 3821044                     |
 |    <raw bytes>                                 |
 |← 200 {"ok":true,"saved":["/home/ice/..."]} ---|
```

手机推送时使用的 token 是 **PC 的 token**（用户在 App 的 "PC token" 输入框里填、
或者扫码 / 被回填得到），和手机自己的 token 是两个独立的值。

### 6.3 扫码配对

```
PC                                              手机
 |  屏幕上显示 afmu://pair?…（§5）               |
 |                                        用户扫码 |
 |← GET /api/info      (X-AFMU-Token: PC 的)  ---|
 |-- 200 {"ok":true,…}  ------------------------→ |
 |← POST /api/pair?token=<手机的>&port=8765   ---|
 |-- 200 {"ok":true}  --------------------------→ |
 |  两个方向的 token 都到位，PC 侧自动连上         |
```

### 6.4 授权连接（PC 上没有手机 token）

```
PC                                              手机
 |-- POST /api/authorize?name=ice-pc&code=4821 -→ |
 |← 200 {"ok":true,"request":"3f9c…","expires":60}|
 |                              弹窗：确认码 4821 |
 |-- GET /api/authorize?request=3f9c… ----------→ |
 |← 200 {"ok":true,"status":"pending"}  ---------|
 |                                     用户点允许 |
 |-- GET /api/authorize?request=3f9c… ----------→ |
 |← 200 {"status":"granted","token":"abc123xyz9"}|
 |-- POST /api/pair?token=<PC 的>  -------------→ |
 |← 200 {"ok":true}  ----------------------------|
```

PC 屏幕上显示的确认码必须和手机弹窗里的一致，用户才应该点允许。

## 7. 版本与兼容

- `protocol` / `afmu` 字段当前为 `1`。
- 新增字段 → 不升版本，客户端必须忽略未知字段。
- 语义变更或删字段 → 升到 `2`，客户端应检查并拒绝不认识的大版本。

> v2 的加密层**没有**升这个字段，因为线格式一个字节都没改：
> 它加的是一层 TLS 和一张配对表。发现应答里的 `rid`（v2 §6.1）同理，
> 是纯增量字段，仍然报 `afmu: 1` —— 升了的话所有 v1 设备会按上面这条
> 直接拒绝掉 v2 设备的应答。

### v1 的新增接口

`/api/authorize`（§3.8）、`/api/pair`（§3.9）和配对二维码（§5）都是**纯新增**，
线格式没变，仍然是 v1：

- 两个接口都**可以不实现**。客户端必须能分辨「不支持」（`404`，或把 `/api/*`
  一律先过 token 检查而返回的 `401`）和「失败」，并退回手抄 token 的老路子；
- 已有的六个接口、鉴权方式、发现协议一个字都没动；
- 旧客户端连新服务端、新客户端连旧服务端都照常工作。

### v1 的几处澄清

以下几条是补写进来的**错误路径**约定，线格式没变，仍然是 v1。两端实现都已按此对齐；
早期实现在这些地方的行为是错的，而不是另有约定：

| 位置 | 澄清 |
|------|------|
| §2.3 | 拒绝还没读请求体的请求时必须 `Connection: close` |
| §3.4 | 请求体截断 / 没有文件段 → `400`，不能回 `ok:true`；截断只能靠对端 FIN 察觉，Linux 端此时是断连而非 `400`（硬不变量仍守住） |
| §3.5 | 必填参数缺失 → `400`；先判参数再解析路径，否则会误报成 `404` |
| §3.6 | 删除 root 本身 → `403` |
| §4.2 | 文件名恰好是 `.` 或 `..` → `unnamed` |
| §4.3 | `.afmu-part` 必须能追溯到具体的远端文件，否则续传会静默损坏文件 |

畸形的 `Range`（如 `bytes=zz-`）属于客户端错误，回 `416` + `Content-Range: bytes */<total>`，
不要让数字解析异常冒成 `500`。

## 1. 威胁模型

先说清楚防谁、不防谁。没有这一节，后面每个选择都是拍脑袋。

### 1.1 v2 要挡住的

| 攻击者能力 | v1 结果 | v2 目标 |
|---|---|---|
| 同网段被动嗅探（`tcpdump`、Wireshark、路由器镜像口） | token、路径、文件名、文件内容全裸 | 只能看到"两个 IP 之间有 TLS 流量" |
| 主动中间人（ARP 欺骗、恶意 AP、DNS 劫持） | 完全接管：拿 token、改文件、静默转发 | 握手失败，客户端拒绝连接并明确报警 |
| 局域网内的好奇邻居（无 token） | 能探到设备名/系统/端口，能让你弹窗 | 只能探到"这里有个 AFMU 设备"，弹窗需用户先进入配对模式 |
| 拿到旧流量的重放 | 有效（token 长期不变） | 无效（TLS 1.3 前向保密 + 每会话密钥） |
| 拿到你硬盘上的配置文件 | 直接拿到 token，永久访问 | 拿到私钥同样完蛋，但 Android 侧私钥不可导出（见 §3.2） |

### 1.2 v2 明确**不**挡的

诚实列出来，免得产生虚假的安全感：

- **流量分析**。加密之后，包大小和时序仍然泄露文件大小、传输时刻、大致数量。
  要挡这个得做填充和恒定速率发送，代价大到不值得，除非你有具体的威胁。
- **端点失陷**。对方设备被 root/植入木马，任何传输层加密都救不了。
- **配对那一刻的物理旁观**。有人站你背后看你扫码，他也拿到了。
- **拒绝服务**。局域网里谁都能打满你的端口。限速能缓解，挡不住。
- **设备存在性**。只要你在同一网段监听端口，"这台机器上有东西在跑"就藏不住。
  §6 只能把"这是 AFMU、叫 icelab、跑 Linux"降级成"这里有个东西"。

## 2. 选型：为什么是双向 TLS，不是别的

三条路都认真评估过，结论写在这里，省得以后再吵一遍。

| 方案 | 结论 | 理由 |
|---|---|---|
| **双向 TLS 1.3 + 指纹钉扎** | ✅ **采用** | 两端都有一流的原生支持（Qt 6.4+ 有 `QSslServer`，Android 有 JSSE + AndroidKeyStore）。握手、前向保密、重协商、降级防护全部由久经审计的实现负责，我们只写"钉扎"这一小块 |
| Noise_XK + libsodium | ❌ 不采用 | 密码学上同样好，但两端都要引新依赖，且握手要自己实现。手写握手是这类项目最常出事的地方——省下的复杂度还不如 X.509 的啰嗦 |
| 沿用 token 派生对称密钥加密 body | ❌ 不采用 | 改动最小，但**只防被动嗅探**：配对那一刻仍然明文，主动 MITM 照样接管；而且路径、文件名仍在 URL 里明文。不满足零信任 |

TLS 1.3 还有一条常被忽略的好处，正好对上你的需求：
**TLS 1.3 把证书消息本身也加密了**（在 ServerHello 之后用握手密钥保护），
所以嗅探者连"这两台设备的身份是什么"都看不到。TLS 1.2 做不到这一点，
所以 v2 **强制 TLS 1.3 下限**，不是"建议"。

## 3. 身份：证书从哪来

v2 的核心变化：**设备身份 = 一对长期密钥**，token 退居次要位置（§7）。

### 3.1 指纹的定义

```
fingerprint = SHA-256( DER(SubjectPublicKeyInfo) )
```

**钉 SPKI 而不是钉整张证书**：这样将来证书到期要重签、或者要改 subject，
公钥不变则所有已配对关系继续有效。钉整张证书的话，每次重签都要全部重新配对。

「SPKI」指的是**算法标识 + 公钥位串那一整层封装**，不是裸的 EC 点。
判据：它必须等于下面这条命令的输出——

```bash
openssl x509 -in identity.pem -pubkey -noout \
  | openssl pkey -pubin -outform DER | sha256sum
```

> **最容易踩的坑**：`openssl x509 -noout -fingerprint -sha256` 算的是**整张证书**的哈希，
> 和这里要的完全不是一个值。两端只要有一端理解错，症状就是
> 「证书明明对却一直不匹配」，而且要等握手层调通之后才会暴露。
> 所以 §12 第 1 步要求做完身份层立刻交叉验证。

展示给用户时用 base32（字母表去掉 `I` 和 `O`——`0` 和 `1` 本来就不在 base32 里），
5 个一组。**256 bit 编成 52 个字符**（51 组之后还剩 1 bit，左对齐补成第 52 组）：

```
U9UZA VEAGM S6NZ4 GCC9E DTGS2 22BGS HMG9H GDG8D XGXGL YLP7S GA
```

**不要截断。** 二维码里的 `fp` 和配对表里存的都是完整的 52 个字符：
二维码容量在这里根本不是约束，为省十几个字符去削弱钉扎强度没有任何收益。
用户比对时嫌长的话，那是 §4.2 的 SAS 要解决的问题，不该靠截断指纹来凑合。

**读回来时跳过哪些字符，两端必须是同一份显式的表**，不能问平台「这算不算空白」：

```
空格 U+0020、tab、换行、回车、连字符 -
U+00A0（不间断空格）、U+2007、U+202F、U+3000（全角空格）
```

`QChar::isSpace()` 认后面那几个，Kotlin 的 `Char.isWhitespace()` **不认**
（U+00A0 / U+2007 / U+202F 在 JVM 上返回 false）。各问各的平台，同一个指纹串
就会一端解得出、另一端拒掉 —— 而指纹恰恰是用来复制粘贴的，从网页里粘出来带个
不间断空格很常见。

表里没有的字符仍然**整串作废**：跳过的是分隔符，不是「看不懂的字符」。
后者是 `QByteArray::fromHex` 那个坑（见 §4.2.3）。

同理，末字符低 4 bit 是填充位，进配对表前必须解码再编码一遍归一 —— 理由见 §4.3。

### 3.2 密钥怎么生成

| 端 | 做法 | 备注 |
|---|---|---|
| **Android** | `KeyGenParameterSpec` + `AndroidKeyStore`，`PURPOSE_SIGN`，`setDigests(DIGEST_NONE, DIGEST_SHA256)`，`setCertificateSubject()` 自签 | **无需任何新依赖**。私钥落在 TEE/StrongBox 里**不可导出**——就算 App 数据被拖走也拿不到身份。通过自定义 `X509KeyManager` 接进 `SSLContext`。`DIGEST_NONE` 不是可选的，见下 |
| **Linux** | 直接调 OpenSSL（Qt 已经链了）生成 EC P-256 自签证书，写到 `$XDG_CONFIG_HOME/afmu/identity.pem`，权限 `0600` | Qt 没有证书生成 API，这段要写 ~80 行 OpenSSL。**不要**在配置 JSON 里存私钥 |

参数统一：**EC P-256**（不是 RSA——生成快、握手包小、Android KeyStore 原生支持），
有效期 20 年（钉扎之后有效期本来就没有意义，只是别让 TLS 栈以过期为由拒绝）。

> **Android 的密钥必须允许 `DIGEST_NONE`，这一条只有真机会告诉你。**
>
> TLS 1.3 自己算握手转录的哈希，然后要求密钥对那 32 字节做**裸 ECDSA 签名**
> （`NONEwithECDSA`）。只允许 `DIGEST_SHA256` 的密钥会被 KeyMint 以
> `INCOMPATIBLE_DIGEST` 拒绝，而错误一路冒到应用层变成
> `SSLHandshakeException: I/O error during system call` ——
> 密钥读得出、证书解得开、指纹显示正常、`openssl s_client` 那边只看到连接被断开，
> **没有任何东西指向密钥**。只有翻 `keystore2` 的 logcat 才看得到真正的原因。
> `DIGEST_SHA256` 留着是给自签证书本身用的。

两端共通的两条规矩：

- **生成是一次性的。** 换了密钥就等于换了设备，所有已配对关系全部作废。
  所以身份**存在但读不出来**时必须**报错**，绝不能当成"重新生成一个"的理由——
  静默换钥匙的表现是"所有已配对设备突然都连不上了"，而且没人查得出原因。

  **一个例外，而且它不是例外：签不动的密钥。** Android 侧启动时会拿密钥真签一次
  32 字节（见上）。签不动就说明它永远握不上手，而它看起来一切正常 ——
  这种密钥**从来没有完成过一次握手**，不可能有任何配对关系依赖它。所以明说并
  重新生成，而不是让用户抱着一块砖头。装过早期版本的设备正是这种状态。
- **subject 只是占位**（`CN=AFMU device`）。钉的是公钥，名字放什么都不影响安全性；
  放设备名反而会把它印进配对表和日志。

## 4. 配对：指纹如何带外交换

这是整个 v2 唯一真正需要用户参与的地方，也是 MITM 的唯一窗口。
**两条路，强度不同，必须让用户知道差别。**

### 4.1 扫码配对（强 —— 推荐路径）

二维码里直接带完整指纹。带外通道（摄像头看屏幕）不经过网络，MITM 无从下手。

```
afmu://pair?v=2&host=192.168.1.30&hosts=192.168.1.30,10.42.0.1&port=8765
  &fp=K7M2Q9XFHTB4NRW2PLDS8VCGYM3JKA7QZE
  &name=ice-desktop&os=linux
```

| 参数 | v1 | v2 | 说明 |
|---|---|---|---|
| `v` | 1 | **2** | v2 客户端见到 `v=1` 要走 §8 的降级流程 |
| `fp` | — | **必填** | 展示方的 SPKI 指纹，base32 |
| `token` | 必填 | **移除** | 身份由证书承担，不再需要把长期密码印在二维码上 |

扫描方拿到 `fp` 之后：钉住它 → 逐个地址建 TLS 连接 → **握手时对端证书的
SPKI 指纹必须等于 `fp`，不等就断开并报"这不是你扫的那台设备"**，绝不放行。

> v1 的二维码里是明文 token，截图/转发/投屏等于交出访问权。
> v2 的二维码里只有公钥指纹，**泄露它不会造成任何损失**——它本来就是公开信息。
> 这是 v2 顺手解决的一个真问题。

### 4.2 授权连接（较弱 —— 无二维码时的路径）

v1 的 `/api/authorize` 流程保留，但确认码的含义变了。

v1 里 4 位确认码由请求方随便生成，只能防"我点的到底是不是这一下"，
**对 MITM 毫无作用**——中间人可以把自己的码转发过去。

v2 改成 **SAS（短认证串）**，两端各自算出同一个 8 字符串，用户比对。

#### 4.2.1 为什么不能只哈希两个指纹

最直觉的做法是：

```
sas = base32( SHA-256( min(fp_a, fp_b) || max(fp_a, fp_b) ) )[0:8]   ← 不安全，不要用
```

它**挡不住中间人**，原因是这里的攻击不是原像而是**碰撞**：

中间人 M 对 A 出示证书 M1、对 B 出示 M2。于是
A 算的是 `f(M1) = SAS(fp_A, fp_M1)`，B 算的是 `g(M2) = SAS(fp_M2, fp_B)`。
M 不需要撞上某个指定值，他只要找到**任意一对** `(M1, M2)` 使 `f(M1) == g(M2)`。
这是生日攻击：各生成约 2²⁰ 个候选密钥对、分别求值、找碰撞，
期望命中一次。**2²⁰ ≈ 100 万次 P-256 密钥生成，单核一两分钟。**

更糟的是它可以**离线**做完。`fp_A`、`fp_B` 是长期公开身份，M 事先扮演一次
客户端／服务端就能探到，然后慢慢磨出 M1/M2，攻击当场零延迟。

> 把 SAS 加长到 12–16 字符能把成本抬到 2³⁰–2⁴⁰，但那是在用 UX 换安全边际，
> 而且方向是错的——真正该做的是让离线预计算失效。

#### 4.2.2 采用的方案：commit-reveal 绑定会话随机数

标准解法是把一对**会话唯一的随机数**拌进 SAS，并用"先承诺后揭示"保证
谁都无法在看到对方随机数之后再挑自己的。这是 ZRTP 和 Signal 安全号码的成熟做法。

发起方为 A（客户端），接收方为 B（服务端）。全程在已建立的 TLS 之内：

```
1. A → B:  commit = SHA-256(n_a)        n_a 是 32 字节 CSPRNG 随机数，此时不公开
2. B → A:  n_b                          B 的 32 字节随机数，明文
3. A → B:  n_a                          揭示；B 必须校验 SHA-256(n_a) == commit，不等立即断开
4. 两端各自计算并显示：

   sas = base32( SHA-256( "AFMU-SAS-v2" || min(fp_a,fp_b) || max(fp_a,fp_b) || n_a || n_b ) )[0:8]
   显示成 XXXX-XXXX
```

- 第 1 步的 commit 是关键：B 在选 `n_b` 时看不到 `n_a`，A 在提交 `n_a` 时看不到 `n_b`。
  谁都无法针对对方的取值去搜碰撞。
- 于是 M 的 2²⁰ 次搜索**必须在线、实时、针对这一次会话完成**——而用户几秒之内就比对完了。
  离线预计算彻底作废，8 个字符（40 bit）足够。
- `min`/`max` 排序保证两端算出同一个值，与谁是客户端无关。
  **排序按无符号字节比较。** 这一条必须写死：Kotlin 的 `Byte` 和 C 的 `char` 都可能是
  有符号的，按有符号排的话 `0x80` 开头的指纹会排到 `0x00` 开头的前面，于是
  **大约一半的指纹对会被两端排成相反的顺序**。这种 bug 测试时看不出来
  （小值向量恰好一致），装到用户手上一半设备对不上，而症状是两个屏幕显示不同的码 ——
  用户唯一合理的反应是认为自己正在被攻击。
- **随机数不排序。** `n_a` 和 `n_b` 的角色是固定的（发起方 / 接收方），
  排序会白白丢掉一半的绑定强度。
- 参数长度不对、或者两个指纹相同 → **必须返回失败**，不能凑一个看起来正常的码出来。
  在该显示码的地方显示空白，等于让用户"比对"一个不存在的东西。
- 域分隔串 `"AFMU-SAS-v2"` 是 ASCII，不含结尾 NUL；将来换算法就换这个串。

#### 4.2.2.1 实现状态与测试向量

两端都已实现（Linux `src/PairSas.{h,cpp}`、Android `core/PairSas.kt`），
并且**三方交叉验证**过：C++、Kotlin，以及一个照着上面公式独立写的脚本，三者一致。

用得上的向量（指纹和随机数都是 32 个相同字节）：

| fp_a | fp_b | n_a | n_b | SAS |
|---|---|---|---|---|
| `0x11…` | `0x22…` | `0x33…` | `0x44…` | `LZ3S-NKNQ` |
| `0x88…` | `0x11…` | `0x33…` | `0x44…` | `NNL9-48XF` |

第二条专门用来钉住无符号排序：`0x88` 当有符号字节是负数，排错了这条就对不上。
再写第三个实现的话，先跑这两条。
- 三个消息里任何一步失败（校验不过、超时、字段缺失）→ 立即断开并**丢弃**该次配对，
  不给"再试一次"按钮复用同一组随机数。

> **为什么不用 TLS keying material exporter（RFC 5705）？**
> 密码学上它更干净——exporter 天然是会话唯一的，一步到位。
> 但 **Qt 完全没有暴露 exporter API**，Android 侧要走 Conscrypt 的非公开接口。
> 两端都拿不到的东西不能写进规范。commit-reveal 只花两个 round-trip，全用得上现成积木。

#### 4.2.3 `POST /api/pair-v2` — 线格式

TLS 已建立但双方都还没钉扎（见 §4.2.4）。**这是此状态下唯一可访问的路由**，
其余一律 `403`，包括 `/` 和 `/api/info`。

**只在 TLS 之内提供。** 明文下调它一律 `400`：没有证书就没有可授权的指纹，
整个交换还会被旁听全看去。

**已配对的连接也要能走到它。** 用户点「允许」那一刻对端就变成已配对，
它随后的轮询走的是已配对连接 —— 只在「未配对」分支路由的话，轮询会撞 `404`，
发起方于是把一次**已经成功**的配对报成超时。会不会撞上取决于客户端有没有复用
连接，这不是任何一端该依赖的东西。

**参数走 query，不走 JSON body**，和 v1 的每一个接口保持一致。
这不只是省事：这个接口对**未认证**的对端开放，让它够得到 body 解析那一整套
（`Content-Length`、chunked、multipart）等于凭空多出一大片攻击面。
query 走的是已经被一致性套件反复捶过的那条路径。响应仍然是 JSON。

**第 1 步 `?step=commit`**

| 参数 | 说明 |
|---|---|
| `step` | `commit` |
| `commit` | `SHA-256(n_a)` 的小写 hex，64 字符。hex 的判定见下 |
| `name` / `os` | 请求方设备名与系统，供 B 的弹窗显示。按 v1 §3.8 的规矩过滤控制字符并截断 |

响应：

```json
{"ok": true, "session": "<32 位 hex>", "nb": "<64 位 hex>", "expires": 60}
```

`session` 是 B 生成的一次性 id，后续两步凭它认人；和 v1 的 `request` id 一样，
**只发给请求方，不写日志**。

> **hex 的判定两端必须逐字一致：偶数长度、只认 ASCII `0-9a-fA-F`、
> 任何一处不合法就整串作废。**
>
> 别把这件事外包给平台，各平台的答案本来就不一样：Qt 的 `QByteArray::fromHex`
> **跳过**看不懂的字符（`"11 22"` 解成 `0x1122`、`"11zz"` 解成 `0x11`），
> Kotlin 的 `Char.digitToInt(16)` 接受**任意 Unicode 十进制数字**
> （`١١` 解得出真实字节）。同一个字符串三种答案，而 `commit` / `na` 正是对端
> **还没被授权**时就能从查询参数塞进来的东西。
>
> 半截解码尤其危险：调用方都按长度校验，而「前 11 字节合法、后面是垃圾」
> 如果解成 11 字节，某个长度刚好对得上的检查就会放它过去。要么全对，要么空。

**第 2 步 `?step=reveal`**

| 参数 | 说明 |
|---|---|
| `step` | `reveal` |
| `session` | 上一步拿到的 id |
| `na` | `n_a` 的小写 hex，64 字符 |

B 校验 `SHA-256(na) == commit`，不等 → `400` 并作废该 session。
通过则两端都能算出 SAS，B 弹窗显示，响应：

```json
{"ok": true, "sas": "K7M2-Q9XF", "expires": 60}
```

> 响应里回带 `sas` 只是让 A 能**自检**双方算出的值一致（防实现 bug）。
> A **必须**自己独立算一遍并显示自己算的那个，**绝不能**显示服务端回的值——
> 否则中间人只要回一个和 A 期望一致的串就骗过去了，整套机制归零。
> 不一致 → 立即断开并报"实现不匹配"，不要显示任何码。

**第 3 步 `GET /api/pair-v2?session=<id>`** — 轮询用户决定

```json
{"ok": true, "status": "pending"}
{"ok": true, "status": "granted", "name": "Pixel 8", "port": 8765}
{"ok": true, "status": "denied"}
{"ok": true, "status": "expired"}
```

`granted` 之后两端各自把对端指纹写进配对表（§4.3）。**响应里没有 token**——
v2 的身份就是那对密钥，没有东西需要交出去。

滥用防护沿用 v1 §3.8 那一套，一条不少：同一时刻只保留一个待决 session（新的回 `429`）、
拒绝后按来源 IP 冷却 60 秒、60 秒超时按拒绝处理、可以整个关掉、服务停止时清空。

**v1 的待决请求和 v2 的待决 session 共用同一个位置**，不是各占一个 ——
分开算的话，两边各来一个就能同时弹两个窗，"一次只受理一个"也就白写了。

#### 4.2.3.1 实现状态

**两端都实现了服务端和客户端**，四个方向都实测过。下表是 Linux 服务端那一轮，
用一个真实的 TLS 客户端逐条验的；Android 服务端的实测见 §5.3。

| 场景 | 结果 |
|---|---|
| 未配对连接访问 `/`、`/api/info`、`/api/list` | 全部 `403`，只有 `/api/pair-v2` 能进 |
| 三步走完 | 服务端回的 SAS 与客户端**独立算出的**一致（真实指纹 + 真实随机数） |
| 已有 session 时再 commit | `429` |
| `na` 与 commit 对不上 | `400`，且**整个 session 作废** |
| 作废之后再拿正确的 `na` 重试 | 仍然 `400` —— 允许重试等于允许一直换 `n_a` 试下去，commit 就白做了 |
| 轮询已作废的 session | `404`（客户端要当 expired 处理，不要当网络错误重试） |
| commit 长度不对 / 未知 step | `400` |

失败原因**不细分**：区分了就等于告诉对方哪一步猜错了。

v1 一致性套件 65 项仍然全过。

#### 4.2.4 与 TLS 的关系

**这三步握手跑在 TLS 之内**：先完成 TLS（双方都还没钉扎，按 §5 的方式取对端 SPKI 指纹
但不做匹配），走完 commit-reveal、用户点"允许"之后，才把对端指纹写进已配对列表。
在此之前，连接除了 `/api/pair-v2` 之外**不得访问任何接口**，包括 `/api/info`。

UI 上的代价：用户要比对 8 个字符而不是 4 个数字。只在没有二维码时才走这条路。

#### 4.2.5 发起配对的三条路

| 发起方式 | 第一个包起就钉扎？ | 抗中间人靠什么 |
|---|---|---|
| 扫二维码（码里有 `fp`） | 是 | 钉扎 **+** 用户比对 SAS |
| 点 `afmu://pair?…` 链接 | 是 —— 和扫码同一个 payload | 同上 |
| 手工输入地址 | 否 —— 此刻还不知道该钉什么 | **只有**用户比对 SAS |

前两条是同一件事的两种到达方式：同一个 payload、同一个解析器、同一条流程。
第二条入口绝不能顺带带来第二套「什么算合法配对码」的规则。
之所以敢让配对码以链接形式传播：码里是公钥指纹，**没有任何秘密**（§4.1）。

手工方式下，第一次请求用一个「记录而不校验」的 TrustManager 拿到对端指纹，
**之后每一步都钉住它**。这条未钉扎的连接之所以可以存在，只因为对端在未配对状态下
除了 `/api/pair-v2` 什么都不放行 —— 这两件事是一对，去掉任何一件另一件就不成立。
那个 TrustManager 被要求校验**客户端**时直接抛异常：它是给一次对外配对连接用的，
装到服务端 socket 上就是「谁都接受」。

### 4.3 已配对之后

指纹存进配对表；此后每次连接都必须匹配，**不匹配一律拒绝，不给"仍然继续"按钮**。
换手机/重装要重新配对——这是钉扎的本意，不是缺陷。

配对表（Linux 侧 `~/.config/afmu/peers.json`，权限 `0600`；Android 侧 SharedPreferences 的 `peersV2` 键）：

```json
[{"fp":"K7M2Q…","name":"Pixel 8","os":"android","lastHost":"192.168.1.42","lastPort":8765,
  "pairedAt":1786000000,"pinned":true}]
```

字段语义，两端必须一致：

| 字段 | 语义 |
|---|---|
| `fp` | **身份本身**。52 字符 base32，进表前一律规范化（见下）。所有查找、去重、钉扎只看它 |
| `name` / `os` | 只为了让用户认出这是哪台设备，可以随时被对端改掉，不参与任何判定 |
| `lastHost` / `lastPort` | **只是重连提示**（§13 问题 3）。多网卡的 PC 换个 IP 是常事，指纹没变就还是同一台机器 |
| `pairedAt` | 首次配对的 Unix 秒。重连**不刷新**它 —— 用户想知道的是"什么时候认识的" |
| `pinned` | 只走 v2，握不上就是失败（§8.1 第 1 条）。由"首次 v2 连接成功"置位，普通更新不得清除 |

**指纹进表前必须规范化。** 52 个 base32 字符是 260 bit 而指纹只有 256 bit，
末字符低 4 bit 是填充位；手抄或者另一个实现可能把它们填成非零，
于是同一个指纹有 16 种写法。解码再编码一遍就都收敛。
不这么做的后果不是不整洁 —— 是表里出现两条指向同一台设备的记录，
**用户删掉一条，另一条还开着门**。

同理，解不出 32 字节的指纹一律**丢弃而不是将就存下**：
存进去的话将来永远匹配不上，症状是"明明配过了却连不上"。丢掉了要在界面上说出来，
否则用户看到的只是"怎么少了一台"。

有意不做的两件事（§13 问题 2）：不限条数，不自动过期。

#### 实现状态

两端都已落地并在用（§12）。当初先做"看和删"、写入留到最后，是有意的：
在 v2 里表里的一条就是一道开着的门，**能开之前先得能关**。

| | 现状 |
|---|---|
| Linux | `src/PeerStore.{h,cpp}`，`QAbstractListModel`，落盘 `peers.json`(0600)；设置页可查看、复制指纹、解除配对 |
| Android | `core/Peers.kt`（纯编解码，不依赖 Android）+ `core/PeerStore.kt`（SharedPreferences）；主界面同样可查看和解除 |
| 测试 | Linux `tests/peerstore_test.cpp`（`-DAFMU_TESTS=ON`）、Android `PeerCodecTest`，两边断言刻意一一对应 |

配对表同时也是「我能连谁」的清单：带地址的记录直接就是可选的对端，
**不必等发现广播**。吃掉 UDP 广播的网络到处都是，只看发现列表的话，
那种网络上所有按钮会一直灰着，旁边却明明白白列着那台机器。

读写都走"读不出来就绝不覆盖"的规矩（Linux 侧抽成 `src/JsonFile.{h,cpp}`，
和 `config.json` 共用）：丢配对关系和丢 token 一样糟 ——
所有设备要重新配对，而用户完全不知道为什么。

## 5. 传输层

| 项 | 要求 |
|---|---|
| 最低版本 | **TLS 1.3**。不接受 1.2 及以下（1.2 不加密证书消息，泄露身份） |
| 套件 | 交给 TLS 栈默认（1.3 的套件集本来就都是 AEAD） |
| 客户端证书 | **必需**。服务端 `VerifyPeer`，双向认证 |
| 证书校验 | 两端都**关掉 CA 链校验**，改为手工比对 SPKI 指纹（自签证书没有 CA 可言）。各端的正确写法见下 |
| SNI | 不发送，或固定发一个常量。别把设备名放进 SNI——那是明文的 |
| ALPN | `afmu/2`，让不匹配的客户端早点失败 |

握手成功 = 双方都持有已钉扎的私钥 = **认证完成**。
未配对的设备连 TLS 都握不上，`/api/*` 整个接口面对陌生人根本不存在。
这比"每个请求检查 token"强一个量级。

### 5.1 "关掉 CA 校验 + 手工钉扎"各端怎么写

这一步最容易写成"看起来能跑但实际没在校验"，两端的正确姿势不一样：

| 端 | 正确写法 | 常见的错误写法 |
|---|---|---|
| **Qt** | `setPeerVerifyMode(QSslSocket::QueryPeer)`，在 `encrypted()` 信号里取 `peerCertificate()` 算 SPKI 指纹并比对，不匹配立刻 `abort()` | ❌ `VerifyNone` + 在 `sslErrors` 里比对。**`VerifyNone` 下 `sslErrors` 不保证触发**，钉扎代码可能一次都不执行 |
| **Android** | 自定义 `X509TrustManager`，在 `checkServerTrusted` / `checkClientTrusted` 里比对 SPKI，不匹配 `throw CertificateException` | ❌ 空实现的 TrustManager + 握手后再检查。握手已经完成，数据可能已经发出去了 |

两端共同的要求：**校验失败必须是异常/断连，不能是一个被忽略的返回值。**

指纹算的是 `SHA-256(DER(SubjectPublicKeyInfo))`（§3.1）——注意是 SPKI 那一层封装，
不是裸公钥点，也不是整张证书。两端实现完之后务必按 §12 第 1 步交叉验证一次。

时序：

```
客户端                                          服务端
 |-- TCP connect ------------------------------→ |
 |-- TLS 1.3 ClientHello (ALPN afmu/2) --------→ |
 |← ServerHello + {加密的} Certificate ---------|
 |   校验 SPKI 指纹 ∈ 已配对表，否则断开          |
 |-- {加密的} Certificate + Finished ----------→ |
 |                校验客户端 SPKI 指纹，否则断开   |
 |========== 之后全部是 v1 的 HTTP 报文 =========|
 |-- GET /api/list?path=/home/ice -------------→ |
 |← 200 {"entries":[…]} -----------------------|
```

**v1 的 HTTP 层一个字都不用改。** v2 只是在下面垫了一层 TLS，
`/api/list`、`/api/upload`、Range 续传、multipart 全部照旧。
这是选 TLS 而不是自定义帧格式的另一个好处：上层代码零改动。

### 5.2 认证的边界

**握手成功 + 对端指纹在配对表里 = 认证完成**，v2 连接上不再检查 token。

这不是省事，是把认证从"每个请求带一个长期共享密钥"换成"对端持有一把被钉扎的私钥"。
留着 token 只会把 v1 的弱点原样搬进 v2（§13 问题 4 已就此拍板）。

反过来说，两个条件缺一不可：

- **只有握手成功不算数。** `QueryPeer` 下客户端不交证书，握手照样成功——
  判空是挡住匿名连接的唯一一道，漏掉它等于把 mTLS 写成了单向 TLS。
- **只有指纹对不上也不算数。** 表里没有就是没有，不给"仍然继续"。

#### 实现状态（Linux 服务端，第 3 步）

没有换成 `QSslServer`：它在 accept 之后立刻开始握手，而 §8.1 第 4 条要求
**先看首字节**再决定这条连接走 TLS 还是 v1 明文。所以仍是 `QTcpServer`，
每条连接建一个 `QSslSocket`，`peek(1)` 之后再 `startServerEncryption()`。
（`peek` 不是 `read`——那个字节属于 ClientHello，读掉的话 TLS 引擎就拼不出完整握手了。）

实测确认，对着运行中的实例逐条验过：

| 场景 | 结果 |
|---|---|
| 带已配对证书连接 | TLS 1.3 握上，ALPN 协商到 `afmu/2`，`/api/info` **不带 token** 直接 200 |
| 不交客户端证书、访客模式关 | 握手成功但被判空，断开 |
| 不交客户端证书、访客模式开 | 放行为访客（浏览器就是这种），日志标明「身份未经验证」，仍需密码 |
| 交了证书但不在配对表 | 放行，但**只够得到 `/api/pair-v2`**，别的一律 403（§4.2.4） |
| 首次 v2 连接成功 | 配对表里该条自动置 `pinned`（§8.2 第 2 阶段） |
| ALPN 不是 `afmu/2` | 握手直接失败（`BAD_EXTENSION`），够不到 HTTP 层 |
| `allowLegacyPlaintext` 关闭 + 明文连接 | **零字节响应**后断开，不回 400 也不回任何 HTTP 报文 |
| `allowLegacyPlaintext` 开启 | v1 一致性套件 65 项全过，行为没有任何变化 |

指纹与 `openssl` 独立算出的值再次交叉验证一致（这次是对端方向）。

#### 实现状态（Linux 客户端，第 4 步）

`QNetworkAccessManager` 走 https，钉扎挂在 **`QNetworkAccessManager::encrypted`** 上——
这个信号的时机正是要害：**握手刚完成、还没有发出任何用户数据**。
在这里 `abort()`，token、路径、文件内容一个字节都不会漏给冒充者。
（实测印证：指纹不匹配那一次，服务端连一条请求记录都没有。）

走不走 TLS 在 `setPeer()` 时就定死：地址在配对表里有记录就必须走 v2，
之后不存在"握手失败就退回明文"的路径（§8.1 第 1 条）。
地址**查不到**记录时还有一个「先试一下加密」模式，见 §8.1 那段注 ——
它退回明文，但只在连接探测那一个请求上，而且只往「本来就没有钉扎期望」的方向退。

Linux ↔ Linux 逐条实测：

| 场景 | 结果 |
|---|---|
| 双方互相配对 | 全程 TLS 1.3，双向钉扎，`/api/info` 不带 token 直接连上 |
| 客户端钉的指纹不对 | 连接中止，界面说"这不是你配对的那台设备"；**服务端没收到任何请求** |
| 已配对对端只提供明文 | 只发出一个 ClientHello 就失败，**没有第二次明文重试**，并说明这是一次有意的拒绝 |
| 地址提示过期、对端其实已配对 | 先试加密 → 按指纹认出 → 就地钉扎 → 地址提示自动修正 |
| 地址提示过期、对端是生人 | 加密但未认证，走 token（和 v1 同级，但线上是密的）|
| 只会 v1 的对端 | 一次失败的 TLS，退回明文重试一次，连上 |
| 对端没配对过 | 照旧走 v1 明文，服务端零条加密连接 |
| 3 MB 下载 + Range 续传 | 字节完全一致（`pumpFile` 的写入节流在 `QSslSocket` 上照常工作）|

##### 两处栽在 Qt 上的坑，都是实测出来的

**1. ALPN 不能当安全边界，因为 QNAM 根本不让你设。**

`QNetworkAccessManager` 会**覆盖**请求里设的 ALPN，自己提 `{h2, http/1.1}`。
服务端只接受 `afmu/2` 的话，第一个连不上的就是我们自己的客户端（`BAD_EXTENSION`）。
所以服务端的 ALPN 列表是 `{afmu/2, http/1.1}`，由服务端在 ALPN 阶段选中
`http/1.1`，顺带把 QNAM 默认开启的 HTTP/2 挡掉——比在客户端逐个请求关
`Http2AllowedAttribute` 可靠，后者实测会让握手直接卡死。

于是 §5 那句"让不匹配的客户端早点失败"**在 Qt 这条路上做不到**：随便一个
HTTPS 客户端都能握上手。挡住它的从来不是 ALPN 而是钉扎——没有已配对的
客户端证书，握完也进不去。ALPN 在这里只是个标记。

**2. QNAM 会因为 `sslErrors` 中止连接，`QueryPeer` 拦不住它。**

服务端那边 `QueryPeer` 确实让校验错误变成非致命的，但 QNAM 多一层自己的判断：
没有明确 `ignoreSslErrors()` 就中止（实测 `SslHandshakeFailedError`）。

所以客户端**必须**在 `sslErrors` 里放过自签证书那几种错误。
这看起来很像 §5.1 说的错误写法，区别要说清楚：

- ❌ 错的是**在 `sslErrors` 里做身份判断**——那段代码可能一次都不执行。
- ✅ 这里 `sslErrors` 里一个字节的身份判断都没有，只是告诉 Qt"CA 这条路我们本来就不走"；
  而且**只放过预期内的那几种**，多出任何一种没见过的错误就照旧中止。
  真正的比对在 `encrypted` 里，不匹配就 `abort()`。

仍与 §8.1 第 2 条不同的一处：`allowLegacyPlaintext` **默认开着**，而规则写的是默认关。
那是 §8.2 第 3 阶段的事 —— 两端的 v2 都跑通了，但用户手上还有旧版本，
现在翻默认值等于让他们突然连不上。等旧版本换得差不多了再翻。

### 5.3 实现状态（Android，第 5–6 步）

| | 做法 |
|---|---|
| 服务端 | 接受的 socket 用 `SSLSocketFactory` 包一层，`wantClientAuth`，钉扎在自定义 `X509TrustManager` 里**抛异常** |
| 客户端 | `HttpsURLConnection` + 同一套 KeyManager/TrustManager，`HostnameVerifier` 恒真（名字这个问题已经被钉扎取代） |
| 密钥 | 自己写 `X509ExtendedKeyManager` 返回 KeyStore 里的私钥句柄，不走 `KeyManagerFactory`——私钥不可导出，让工厂去"取"它只会以难查的方式失败 |
| 钉扎失败 | `CertificateException`。**必须是异常**：返回值形式的拒绝会被 TLS 栈忽略，握手照常完成，"校验过了"就成了一句空话 |

#### 在纯 JVM 上验证的（`TlsPinningTest`，11 项）

握手要真机，但最容易错、错了又最难查的几件事不需要：

- **指纹算得对不对**：拿 Linux 端真实生成的一张证书当向量，期望值由 `openssl`
  独立算出。Java 的 `PublicKey.getEncoded()` 与 `i2d_X509_PUBKEY` 逐字节相同，已确认。
  对照组（整张证书的哈希）是不同的值，即钉的确实是 SPKI。
- **不认识的对端会不会被挡住**：未配对指纹抛异常、空证书链抛异常、
  `getAcceptedIssuers` 为空。
- **放行未配对客户端的那个开关只对客户端方向生效**：我们主动连出去时，
  未配对的对端正是要找的那个中间人，那边没有第二道闸门能兜住它。
  开关是现读的，改完设置下一条连接就生效，不用等重启。

#### 一处平台限制，改了设计：**Android 端不做首字节分流**

§8.1 第 4 条的分流要"偷看首字节再把它还给 TLS 引擎"，靠的是
`SSLSocketFactory.createSocket(Socket, InputStream consumed, boolean)`——
**Android 没有这个重载**（平台保留的是 Java 8 之前的签名集，实测编译期就没有）。
偷看过的 ClientHello 字节还不回去，握手就永远完不成。

所以手机一次只提供一种协议，由设置项决定：明文 v1（默认，现有客户端都说这个）
或加密 v2。Linux 端仍然一个端口同时服务两者，因为 Qt 让它 peek。
代价只落在"手机当服务端"这个方向，而且它出现在设置项里，不是藏在某个回退分支里。

#### 模拟器实测（API 37）

握手、AndroidKeyStore 取密钥、包装已 accept 的 socket 都跑通了，两个方向：

| 场景 | 结果 |
|---|---|
| 手机当客户端，连已配对的 PC | 全程钉扎加密，浏览 + 下载，**不带任何 token**，中文文件名完好 |
| 手机当服务端，PC 用 `--pair` 发起 | 三步握手 → 两屏比对码一致 → 允许 → 两端配对表都写入 |
| `openssl s_client` 无客户端证书 | 访客模式开着时放行，日志标明「身份未经验证」；关着时握手阶段就断 |
| 指纹交叉验证 | App 显示的 = `openssl` 从线上证书算的 = Linux 端从对端证书算的 |

**一处必须记住的**：`handle()` 里判定对端身份要从**本条连接的 session** 读证书，
不能从 TrustManager 上的字段读。TrustManager 是所有连接共用的，而 `wantClientAuth`
下不出示证书的客户端**根本不会走到 TrustManager** —— 两件事合起来，一条匿名
连接会继承上一条连接里那台已配对设备的身份，被当成那台设备服务。session 继承不了。

**另一处**：「只接受加密连接」开着但 TLS 没能就绪时，服务端**拒绝连接**而不是
安静地回到明文。开关还显示着「开」却在服务明文，正是这个开关存在的意义所反对的事。

## 6. 发现协议 v2：不再广播设备名

v1 的问题实测过：往 UDP 8766 发一个包，任何人都能拿到
`{"afmu":1,"name":"icelab","os":"linux","port":8765}`。设备名、系统、端口全泄露。

v2 分两种模式：

### 6.1 常态模式（默认）

应答里**不含设备名和系统**，只含一个滚动标识：

```json
{"afmu": 1, "port": 8765, "rid": "6ca38b0b"}
```

```
rid = hex( SHA-256( "AFMU-RID-v2" || fp || 十进制ASCII(floor(unix_time / 300)) )[0:4] )
```

三处定死的细节，都是为了"两端逐字节一致"这一个目的：

- **域分隔串 `AFMU-RID-v2`**，ASCII，不含结尾 NUL。同一个 `fp` 在 SAS 里也进哈希，
  隔开的代价是零。
- **时间窗按十进制 ASCII 编码**。早期草案只写了 `|| floor(...)`，没说几字节、什么
  字节序 —— 这种含糊正是跨实现对不上的经典原因。定成 ASCII 还有个好处：
  一行 shell 就能独立复核。

  ```bash
  { printf 'AFMU-RID-v2'; cat fp.bin; printf '5666667'; } | sha256sum | cut -c1-8
  ```
- **版本号仍是 `afmu: 1`**，不是 2。`rid` 是纯增量字段，v1 设备忽略它即可；
  改成 2 会让所有 v1 设备**直接跳过** v2 设备的应答（§7 规定不认识的大版本要拒绝），
  代价远大于收益。等真正断开 v1 兼容时再改。

- **已配对的设备**手里有对方指纹，能自己算出同样的 `rid`，于是认得出"这是我的 Pixel"。
- 时间窗跨越边界时，接收方同时接受 `t` 和 `t-1` 两个窗口，避免边界抖动。
- 依赖两端时钟大致同步（±5 分钟内），局域网场景成立。
- **取 4 字节（32 bit），不是 2 字节。** 16 bit 在多设备环境下有 1/65536 的误认率，
  而 UDP 应答不差这两个字节。

**这挡住了什么、没挡住什么**（别把它当匿名）：

| 观测者 | 结果 |
|---|---|
| 陌生人**单次**观测 | 只看到一串随机 hex，问不出设备名、系统、身份 ✅ |
| 陌生人**连续**观测多个时间窗 | rid 序列本身就是高熵指纹（3 个窗口 = 96 bit），**仍可关联为同一台设备** ⚠️ |
| 曾经在 §6.2 配对模式下见过该设备 `fp` 的观测者 | 此后**永久**能算出它每个窗口的 rid，追踪能力完整 ⚠️ |

所以准确的说法是：**在从未见过该设备 `fp` 的前提下，单次观测无法识别它是谁；
连续观测仍能把它和自己关联起来。** 要挡住连续观测得让 rid 与观测者不可预测的东西绑定，
而 UDP 广播场景里没有这样的东西——这是广播发现的固有代价，不是实现缺陷。

### 6.2 配对模式（用户显式开启，限时）

只有用户在界面上点了"允许被发现 / 开始配对"，才在 **60 秒内**应答完整信息：

```json
{"afmu": 1, "port": 8765, "name": "icelab", "os": "linux", "fp": "K7M2Q…"}
```

**收到 `fp` 不等于认识它。** 只有已经在配对表里的指纹才算认出来，否则任何人
报一个指纹就能冒充成"你认识的设备"。

超时自动回到常态模式。**这样"陌生人能看到设备名"的窗口从"永远"缩短到
"用户主动开启的那一分钟"。**

> 注意：`fp` 出现在明文 UDP 里是**故意的**，它是公钥指纹，泄露它不会造成访问权损失。
> 但它是**长期不变的**标识：谁在这 60 秒里抓到了它，此后就能永久算出该设备的 `rid`
> （见 §6.1 的表格）。所以"短暂出现"限制的是被抓到的**概率**，不是被抓到之后的影响——
> 一次泄露 = 永久可追踪。这是配对便利性的实际代价，接受它，但别说成"没有代价"。

## 7. token 的去向

v2 里 **token 不再是 `/api/*` 的认证手段**——认证由 mTLS 完成。

保留 token 只为一件事：**浏览器界面**（§9）。配置项从"访问 token"改名为
"浏览器访问密码"，并且默认**不生成**，用户开启浏览器界面时才生成。

顺带解决 v1 的一个实测问题：`?token=` 允许 token 出现在 URL 里，
会落进代理日志、浏览器历史、Referer。v2 的 `/api/*` **不再接受任何 query 里的凭证**。

## 8. 与 v1 的兼容和降级防护

这一节最容易写错，写错了 v2 就白做——攻击者只要伪装成 v1 设备就能把你打回明文。

### 8.1 规则

1. **配对表里 `pinned: true` 的对端，永远只走 v2。** 对它发起的连接如果
   TLS 握手失败，就是失败，**绝不回退到明文 HTTP**。这是降级攻击的唯一防线。
2. 从没配对过的设备，允许在用户明确同意后走 v1 明文，但界面上必须
   持续显示"未加密"状态，且默认关闭（设置项：`allowLegacyPlaintext`，默认 `false`）。
3. v2 设备的发现应答是 `afmu:2`；v1 客户端会因为 `afmu != 1` 直接忽略（
   本次审查已经把两端的版本判定统一成严格相等，正好为此铺路）。
4. 端口：v2 用**同一个 8765**。服务端在 accept 后偷看第一个字节：
   `0x16` 是 TLS ClientHello，其它按 v1 明文处理（仅当 `allowLegacyPlaintext` 开启）。
   这样一个端口同时服务新旧客户端，不用占两个端口。
   **`allowLegacyPlaintext` 关闭时，非 `0x16` 首字节一律直接断开**，不要回 400、
   不要回任何 HTTP 报文——零信任模式下这个端口在效果上只听 TLS。

> **第 1 条靠什么知道「这个对端在配对表里」？** 靠地址反查（`findByAddressHint`）：
> 连之前只有地址可用，身份要握完手才知道。地址在正常路径上够用 —— 发现协议的
> 滚动 `rid`（§6.1）会在见到设备时刷新它的地址提示，所以表里的地址通常是新的。
>
> 它兜不住的只有一种情况：**用户手工输入了一个发现没见过的地址**。查不到记录
> 就不钉扎，而对面可能正是早就配过的那台设备，于是连接退回明文。
>
> 客户端为此多了一个「先试一下加密」的模式：地址查不到记录、但配对表非空时，
> **不带期望值先走一次 TLS**，握手完成后按指纹认人 ——
>
> | 握手结果 | 处理 |
> |---|---|
> | 指纹在表里 | 当场变成钉扎连接，刷新地址提示，下次直接命中 |
> | 指纹不在表里 | 生人。连接是加密的但未认证，和 v1 同级（仍要 token） |
> | 握手失败 | 对面多半只会 v1，**仅在连接建立那一刻**退回明文重试一次 |
>
> 判定发生在 `encrypted` 上，也就是任何请求数据发出之前 —— 和正常钉扎是同一个
> 时机，不是 §5.1 说的那种「先连上再验」。
>
> 那次明文重试**只在连接探测这一个请求上发生**，别的请求路径一概不碰：
> 一个会自己换协议重发的客户端正是降级攻击最想要的东西。它之所以可以存在，
> 是因为它只往「本来就没有钉扎期望」的方向退 —— 地址命中记录时永远不重试，
> 那时候握手失败就是失败。

> **第 1 条只保护客户端，服务端侧需要第 4 条那半句才完整。**
> 首字节分流发生在 TLS 握手之前，也就是在服务端知道对面是谁之前，
> 所以服务端无法判断"这个明文连接是不是来自某个 `pinned` 对端"，
> 没法像客户端那样按对端身份拒绝回退。
> 服务端能做的只有一刀切：要么整个进程允许明文，要么完全不允许。
> 这不是漏洞（v1 路径仍然要 token），但别指望 `pinned` 标志在服务端方向上起作用。

### 8.2 升级路径

| 阶段 | Android | Linux | 用户感知 |
|---|---|---|---|
| 1 | 双栈：能收 v1 也能收 v2 | 同左 | 无 |
| 2 | 已配对设备自动升级到 v2（首次 v2 连接成功后写 `pinned:true`） | 同左 | 提示"已启用加密" |
| 3 | `allowLegacyPlaintext` 默认关 | 同左 | 老设备需手动放行 |
| 4 | 删除 v1 明文路径 | 同左 | 必须都升级 |

## 9. 访客模式（浏览器界面的去向）

`WebUi.kt` 那个自包含单页是 v1 的一大卖点：PC 上什么都不装就能收发。
**它无法达到 v2 的安全标准，而且再怎么实现也达不到**：

- 浏览器不会拿客户端证书去做 mTLS（除非用户手工装一张，UX 灾难）。
- 自签服务端证书只会弹一个"不安全"警告，用户点"继续"那一下，
  就等于亲手关掉了中间人防护。

所以它降级为一个显式的**访客模式**，并且照实说清楚它是什么。

### 9.1 三个开关怎么组合

| 设置项 | 含义 |
|---|---|
| `zeroTrustMode` | 总闸：只认配对表 + 只听加密。打开时压掉下面两个 |
| `allowLegacyPlaintext` | 接不接受非 TLS 的连接（§8.1） |
| `guestMode` | 密码认证这条路开不开；Android 上同时决定网页界面服不服务 |

服务端只该问**实际生效**的那个值：`guestMode && !zeroTrustMode`。
界面上零信任打开时，另外两个开关**置灰而不隐藏** ——
消失了的开关会让用户对着"网页怎么打不开了"毫无头绪。

### 9.2 访客模式开着时

- 密码认证（v1 那套）有效，来源是不是已配对设备都行。
- Linux 端：明文和 HTTPS 都能进，因为它做首字节分流。
- Android 端：一次只能一种，由 `allowLegacyPlaintext` 决定（原因见 §5.3）。
- **必须放行没有客户端证书的 TLS 连接** —— 浏览器永远不出示证书，
  不放行的话"HTTPS 的访客模式"根本用不了，而那正是这里推荐的配置。
  放行之后它也只是访客：这条连接全程算未配对，后面还有密码那道门。
- 网页界面顶部常驻一条不可关闭的说明。**关得掉的警示等于没有。**

### 9.3 访客模式关掉时

- 任何 token 都不算数，不留"密码对了还是放行"的后门。
- `/api/authorize` 一并挡住：它的作用是把 token 发出去，而这时候 token
  什么都打不开。**发一个用不了的凭证，比明说"这条路关了"糟得多** ——
  用户会拿着它反复试，然后去查网络、查防火墙。
- 网页界面不是"登录失败"，而是根本不提供，返回一页说明。
  一个永远登不进去的登录框只会让人把密码输二十遍。
- 回的是 `403` + `{"error": "guest mode is off; pair over an encrypted connection"}`，
  和"token 猜错"的 `401` 分开 —— 后者会触发退避，而这里再试一百次也一样，
  退避没有意义，说清楚才有。

### 9.4 界面上必须显示当前实际是哪种状态

服务开着的时候，界面上常驻一条说明，**不可关闭**：情况没变，而三周前点掉的一个
提示不算今天的知情同意。

**但它必须说实话。** 这条横幅原来是无条件的「未加密」—— v1 时代那是对的，
而零信任模式一开始拒绝明文，它就成了假的。一条恒真的警告等于训练用户忽略它，
下次它真该响的时候没人会看。所以它跟着**实际生效**的状态走：

| 状态 | 说法 |
|---|---|
| 加密不可用 | 未加密：同一网络里的任何人都能看到文件名和内容 |
| 明文开着 | 已配对的走加密，其余仍是明文 |
| 只加密 + 访客开 | 挡得住偷听，但访客的身份未经验证 |
| 只接受已配对 | 闭锁：这是 v2 完整的那道防线 |
| 只加密但 TLS 没就绪 | **谁也连不上** —— 服务端拒绝所有连接，不会安静地回到明文 |

最后一行是个安全属性而不只是文案：开关显示着「开」却在服务明文，
正是这个开关存在的意义所反对的事。

### 9.5 默认值：新装关，升级开

草案原本要求一律默认关。**落地时改成了两个默认值**，理由是：

- 默认关是对的，密码认证挡不住中间人；
- 但对已经在用网页界面的人来说，升级一次它就打不开了，而且没有任何提示，
  表现是"今天开始网页进不去了"。这和静默换密钥是同一类问题 ——
  都是用户完全无从下手的那种。

所以只有**配置从来不存在**（真·新装）才默认关。两种情况都会把值写进配置，
于是设置页上看到的就是实际生效的值，不留任何隐式行为。

判断必须是一次性的、在固定时机做的：Android 侧的 token 是首次读取时才铸的，
"配置里有没有键"会因为谁先被读而给出不同答案。所以它放在 `Prefs` 构造里，
不是塞进某个 getter 的默认值。

## 10. 加密之后还剩什么泄露

| 泄露项 | 是否可见 | 能否缓解 |
|---|---|---|
| 两个 IP 之间有连接、端口 8765 | ✅ 可见 | 不能（换端口只是障眼法） |
| 传输时刻、持续时长 | ✅ 可见 | 不能 |
| 传输字节量 → 文件大小 | ✅ 可见 | 填充可缓解，代价大，**建议不做** |
| 文件名、路径、目录结构 | ❌ 不可见 | TLS 已解决 |
| 设备名、系统、身份 | ❌ 不可见 | TLS 1.3 加密证书 + §6 滚动 rid |
| token / 凭证 | ❌ 不可见 | 已不在传输中 |
| "这是 AFMU 协议" | ⚠️ 可推断 | ALPN 明文含 `afmu/2`；在意的话可去掉 ALPN，代价是失败诊断变差 |

最后一行值得单独说：如果你的威胁模型里"被发现在用这个工具"本身就是问题，
那要做的是流量混淆，那是另一个量级的工程，不建议在局域网工具里做。

## 11. 不依赖 v2、现在就能做的收敛

v2 是大工程。下面这些**不改协议、不破兼容**，可以立刻落地，
把 v1 在半可信网络（比如公司内网）下的暴露面压下去：

| # | 改动 | 收益 | 工作量 |
|---|---|---|---|
| A1 | `/api/*` 不再接受 `?token=`；浏览器下载改用**短时下载券**（见下） | token 不再进日志/历史/Referer | 小 |
| A2 | 发现应答默认不含 `name`/`os`，改为用户开启"配对模式"时才带 | 关掉最直接的元数据泄露，且是 §6 的前置工作 | 小 |
| A3 | `/api/authorize` 按来源 IP 限速 + 全局冷却，拒绝后延长封禁 | 挡住弹窗骚扰和换 ID 刷屏 | 小 |
| A4 | token 校验失败计数：同一 IP 连续失败 N 次后指数退避 | 实测 200 次错误尝试 0.78 秒无任何惩罚；补上纵深 | 小 |
| A5 | `Host` 头白名单（只认本机 LAN 地址 / `.local`），并对浏览器界面加 `Origin` 校验 | 挡 DNS-rebinding 和跨站请求 | 小 |
| A6 | 界面上把"未加密"状态常驻显示，别只写在文档里 | 用户知情 | 很小 |

### 11.1 A1 的短时下载券

浏览器的 `<a href>` 没法带自定义头，这是 `?token=` 当初存在的唯一理由。
替代物要定义清楚才能实现，三个点都得说死：

```
GET /api/download?path=…&ticket=<exp>.<mac>

exp = 过期的 Unix 秒（十进制）
mac = base64url( HMAC-SHA256( token, "afmu-dl-v1\n" || exp || "\n" || path ) )[0:22]
```

- **防伪造**：MAC 用本机 token 当密钥，服务端**无状态**校验，不用记任何东西。
  域分隔前缀防止这个 MAC 将来被别的用途复用。券绑定 `path`，换个路径就失效。
- **过期语义**：`exp` 约束的是"**开始**下载"，不是整个传输。
  服务端在决定响应之前校验一次 `now <= exp`，一旦开始写响应体就不再看——
  否则 5 秒过期等于禁止下载任何大于几十 MB 的文件。签发时给 `exp = now + 5` 就够，
  用户点链接是立刻发生的事。
- **不叫"一次性"**。真一次性要服务端记已用 nonce，和上面的无状态校验直接矛盾。
  二选一，这里选无状态：券在 5 秒窗口内可重放，但它只能重放**同一个路径的下载**，
  且窗口短到没有实际转发价值。想要真一次性就得接受一张服务端状态表，不值得。

发券的地方是浏览器界面自己（已经过了密码认证），页面上的每个下载链接现拼现用。

**建议顺序：先做 A1–A6（一两天），再评估 v2 要不要上。**
A 组做完之后，v1 在公司内网这种"半可信"环境下就基本够用了；
v2 是为咖啡厅 Wi-Fi 那种真正的零信任场景准备的。

## 12. 实施清单（as-built）

按依赖顺序，每项都独立提交过。留着这份清单是因为正文和代码注释里好几处按步骤号引用它。

1. **身份层**：两端生成/持久化 EC P-256 密钥与自签证书；SPKI 指纹计算与 base32 展示。

   **做完立刻交叉验证指纹，别等到第 3 步。** 两端各打印一次自己算出的指纹，
   再用外部工具独立算一遍，三个值必须完全相同：

   ```bash
   openssl x509 -in cert.pem -pubkey -noout \
     | openssl pkey -pubin -outform DER \
     | sha256sum
   ```

   mTLS 手工钉扎最常见的翻车就是两边对"SPKI"的理解差一层封装
   （有人哈希了整张证书，有人哈希了裸 EC 点）。握手层调通之后再发现这个，
   现象是"证书明明对却一直不匹配"，非常难查。这一步 10 分钟，省半天。

2. **配对表**：`peers.json` / SharedPreferences 结构，增删查改 + 界面。**已完成**
3. **Linux 服务端**：首字节分流 + `QSslSocket` 手工升级，`QueryPeer` + 手工指纹比对。
   **已完成** —— 没用 `QSslServer`，原因在 §5.2。
4. **Linux 客户端**：`QNetworkAccessManager` 走 https，钉扎挂在 `encrypted` 上
   （**不是** `sslErrors`，原因见 §5.2）。**已完成**
5. **Android 服务端**：包装已 accept 的 socket + AndroidKeyStore 的 `X509KeyManager`
   + 自定义 `X509TrustManager`。**已完成，模拟器实测通过**；没用 `SSLServerSocket`，
   也不做首字节分流，原因在 §5.3。
6. **Android 客户端**：`HttpsURLConnection` 挂同一套 TrustManager/KeyManager。
   **已完成，模拟器实测通过**
7. **二维码 v2**：`fp` 参数，`token` 移除，`v=2`。**已完成**，两端有跨实现向量（§15）。
8. **SAS 授权流程**：`/api/pair-v2` 三步 commit-reveal（§4.2.3）、8 字符 SAS 与两端 UI。
   注意 A 端必须显示**自己算的** SAS，不是服务端回的那个。
   **已完成，四个方向都实测过**：两端各自都能当发起方和接收方。发起有三条路 ——
   扫码、点 `afmu://pair?…` 链接（和扫码同一个 payload、同一个解析器、同一条流程）、
   手工输地址。前两条码里带指纹，连接从第一个包起就钉扎；第三条此时无从钉扎，
   第一次请求记下对端指纹、之后每一步都钉住它 —— 抗中间人靠的是用户比对 SAS。
9. **发现 v2**：滚动 `rid`（§6.1）+ 配对模式（§6.2）。**已完成**
10. **降级防护**：`pinned` 标志、首字节嗅探分流、`allowLegacyPlaintext` 开关。
    **已完成**；首字节分流只有 Linux 端有，原因见 §5.3。
11. **访客模式**：开关 + HTTPS + 警示文案（§9）。**已完成**
12. 文档：把 v2 草案扶正为本文第二部分。**已完成**

## 13. 拍板过的问题

写实现之前定下来的，连同理由记在这里，省得以后再吵一遍。
编号保持不变，正文和代码注释里按编号引用。

1. **Android 私钥优先 StrongBox，失败降级 TEE，都不行才用软件密钥。**
   界面上照实显示落在哪一层 —— 软件密钥意味着一次完整备份就能把身份带走，
   另外两种不会。

2. **配对表不限条数，不自动过期。** 自动删掉一台半年没用的设备，
   下次用要重新配对，而用户只会觉得"怎么又要配一遍"。要清理只有界面上手动删。

3. **多网卡 PC 换 IP 之后靠 `rid` 认出来**（§6.1），不重新配对。
   `lastHost` 降级为重连提示，不再是身份的一部分 —— 指纹才是身份。

4. **不加 token 作为第二因子。** mTLS 已经够了，多一个长期共享密钥就多一个
   泄露面，而且 UX 直接回到 v1。

   真正想要"就算私钥被偷也还有一道"的话，正确解法不是加共享密钥，而是
   **给密钥本身加锁**：Android 侧在 `KeyGenParameterSpec` 上加
   `setUserAuthenticationRequired(true)` 配合
   `setUserAuthenticationParameters(300, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`，
   于是签名操作需要指纹/PIN，5 分钟内免重复解锁。
   这比第二因子强 —— 密钥在 TEE 里且用不了，不是"被偷了但还有一道" ——
   而且日常 UX 几乎无感。Linux 侧没有等价物（`identity.pem` 就在盘上），
   要对等的话得接系统 keyring，属于 v2 之后的事。

## 14. 还没做的

- **Linux 端读二维码。** PC 一般没摄像头，而且它是显示码的那一方，所以优先级很低。

- **真手机上的验证。** 目前跑通的是模拟器（API 37，软件密钥）。StrongBox / TEE
  那条路只在代码层面成立过 —— 而 §3.2 那个 `DIGEST_NONE` 的教训正说明，
  密钥这一层的问题只有真硬件会告诉你。

- **§8.2 第 3 阶段**：把 `allowLegacyPlaintext` 的默认值翻成关。
  两端的 v2 都跑通、用户手上的旧版本换得差不多了再做。

- **Linux 侧的私钥保护**。`identity.pem` 就在盘上，0600 而已，
  和 Android 的 TEE 不对等。接系统 keyring 是 v2 之后的事。

## 15. 附：跨实现测试向量

两端算得不一样的地方都不会抛异常，只会安静地表现成功能没了 ——
所以每一个都钉了向量。值取自 Linux 端 `afmu_peerstore_test` 的真实输出，
不是照着另一端反填的：那样测的只是"它和自己一致"。

除了下面这些值，还有两处**判定规则**同样必须逐字一致，它们不是向量而是规矩：
hex 的合法性（§4.2.3）和指纹读回时跳过哪些字符（§3.1）。两处都栽在
「问平台什么算合法」上，两个平台的答案本来就不一样。

**SPKI 指纹**（§3.1）：由 `openssl` 独立算出，见 `TlsPinningTest`。

**SAS**（§4.2.2）：

| 输入 | 结果 |
|---|---|
| `fp_a=0x11×32, fp_b=0x22×32, n_a=0x33×32, n_b=0x44×32` | `LZ3S-NKNQ` |
| `fp_a=0x88×32, fp_b=0x11×32, n_a=0x33×32, n_b=0x44×32` | `NNL9-48XF` |

第二组是特意选的：`0x88` 当有符号字节是负数。排序按**无符号**比 ——
按有符号比的话，一半的指纹对会被两端排成相反的顺序，
而症状是两个屏幕显示不同的码，用户只会理解成正在被攻击。

**滚动 rid**（§6.1）：

| 输入 | 结果 |
|---|---|
| `fp=0x11×32, t=1700000250` | `3c438e0d` |
| `fp=0x22×32, t=1700000250` | `08b4ad2c` |
| `fp=0x11×32, t=0` | `5b724de7` |

**配对二维码**（§4.1）：

```
afmu://pair?v=2&host=192.168.1.30&port=8765&fp=CEJTCEJT…CEJS&name=%E5%AE%A2%E5%8E%85%20%E7%94%B5%E8%84%91&os=linux
```

空格是 `%20`，中文是 UTF-8 百分号编码，`+` 保持是加号**不解成空格**。
最后一条只有名字里带加号的那个用户会遇到，也只有他会觉得"名字怎么变了"。
