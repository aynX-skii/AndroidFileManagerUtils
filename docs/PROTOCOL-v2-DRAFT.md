# FileBridge 传输协议 v2 草案 —— 零信任网络下的加密与身份

状态：**草案，实施中**。§12 清单的第 1–6 步（主干）已写完：设备身份、配对表、
两端的服务端与客户端。**Linux ↔ Linux 已实测跑通全程 v2**；Android 一侧
**代码写完但没在真机上跑过**——headless 环境没有 AndroidKeyStore，
能在纯 JVM 上验的都验了（见 §5.3），握手本身必须上真机确认。
配对还得手工填指纹（二维码 v2 与 SAS 是第 7–8 步），所以日常仍走
v1（[PROTOCOL.md](PROTOCOL.md)）。

这份文档只回答一个问题：**怎么让 AFMU 在不可信网络上也能用。**
v1 自己写着"不要在不可信网络上开启服务"，v2 的目标就是删掉那句话。

## 1. 威胁模型

先说清楚防谁、不防谁。没有这一节，后面每个选择都是拍脑袋。

### 1.1 v2 要挡住的

| 攻击者能力 | v1 结果 | v2 目标 |
|---|---|---|
| 同网段被动嗅探（`tcpdump`、Wireshark、路由器镜像口） | token、路径、文件名、文件内容全裸 | 只能看到"两个 IP 之间有 TLS 流量" |
| 主动中间人（ARP 欺骗、恶意 AP、DNS 劫持） | 完全接管：拿 token、改文件、静默转发 | 握手失败，客户端拒绝连接并明确报警 |
| 局域网内的好奇邻居（无 token） | 能探到设备名/系统/端口，能让你弹窗 | 只能探到"这里有个 AFMU 设备"，弹窗需用户先进入配对模式 |
| 拿到旧流量的重放 | 有效（token 长期不变） | 无效（TLS 1.3 前向保密 + 每会话密钥） |
| 拿到你硬盘上的配置文件 | 直接拿到 token，永久访问 | 拿到私钥同样完蛋，但 Android 侧私钥不可导出（见 §3.2） |

### 1.2 v2 明确**不**挡的

诚实列出来，免得产生虚假的安全感：

- **流量分析**。加密之后，包大小和时序仍然泄露文件大小、传输时刻、大致数量。
  要挡这个得做填充和恒定速率发送，代价大到不值得，除非你有具体的威胁。
- **端点失陷**。对方设备被 root/植入木马，任何传输层加密都救不了。
- **配对那一刻的物理旁观**。有人站你背后看你扫码，他也拿到了。
- **拒绝服务**。局域网里谁都能打满你的端口。限速能缓解，挡不住。
- **设备存在性**。只要你在同一网段监听端口，"这台机器上有东西在跑"就藏不住。
  §6 只能把"这是 AFMU、叫 icelab、跑 Linux"降级成"这里有个东西"。

## 2. 选型：为什么是双向 TLS，不是别的

三条路都认真评估过，结论写在这里，省得以后再吵一遍。

| 方案 | 结论 | 理由 |
|---|---|---|
| **双向 TLS 1.3 + 指纹钉扎** | ✅ **采用** | 两端都有一流的原生支持（Qt 6.4+ 有 `QSslServer`，Android 有 JSSE + AndroidKeyStore）。握手、前向保密、重协商、降级防护全部由久经审计的实现负责，我们只写"钉扎"这一小块 |
| Noise_XK + libsodium | ❌ 不采用 | 密码学上同样好，但两端都要引新依赖，且握手要自己实现。手写握手是这类项目最常出事的地方——省下的复杂度还不如 X.509 的啰嗦 |
| 沿用 token 派生对称密钥加密 body | ❌ 不采用 | 改动最小，但**只防被动嗅探**：配对那一刻仍然明文，主动 MITM 照样接管；而且路径、文件名仍在 URL 里明文。不满足零信任 |

TLS 1.3 还有一条常被忽略的好处，正好对上你的需求：
**TLS 1.3 把证书消息本身也加密了**（在 ServerHello 之后用握手密钥保护），
所以嗅探者连"这两台设备的身份是什么"都看不到。TLS 1.2 做不到这一点，
所以 v2 **强制 TLS 1.3 下限**，不是"建议"。

## 3. 身份：证书从哪来

v2 的核心变化：**设备身份 = 一对长期密钥**，token 退居次要位置（§7）。

### 3.1 指纹的定义

```
fingerprint = SHA-256( DER(SubjectPublicKeyInfo) )
```

**钉 SPKI 而不是钉整张证书**：这样将来证书到期要重签、或者要改 subject，
公钥不变则所有已配对关系继续有效。钉整张证书的话，每次重签都要全部重新配对。

「SPKI」指的是**算法标识 + 公钥位串那一整层封装**，不是裸的 EC 点。
判据：它必须等于下面这条命令的输出——

```bash
openssl x509 -in identity.pem -pubkey -noout \
  | openssl pkey -pubin -outform DER | sha256sum
```

> **最容易踩的坑**：`openssl x509 -noout -fingerprint -sha256` 算的是**整张证书**的哈希，
> 和这里要的完全不是一个值。两端只要有一端理解错，症状就是
> 「证书明明对却一直不匹配」，而且要等握手层调通之后才会暴露。
> 所以 §12 第 1 步要求做完身份层立刻交叉验证。

展示给用户时用 base32（字母表去掉 `I` 和 `O`——`0` 和 `1` 本来就不在 base32 里），
5 个一组。**256 bit 编成 52 个字符**（51 组之后还剩 1 bit，左对齐补成第 52 组）：

```
U9UZA VEAGM S6NZ4 GCC9E DTGS2 22BGS HMG9H GDG8D XGXGL YLP7S GA
```

**不要截断。** 二维码里的 `fp` 和配对表里存的都是完整的 52 个字符：
二维码容量在这里根本不是约束，为省十几个字符去削弱钉扎强度没有任何收益。
用户比对时嫌长的话，那是 §4.2 的 SAS 要解决的问题，不该靠截断指纹来凑合。

### 3.2 密钥怎么生成

| 端 | 做法 | 备注 |
|---|---|---|
| **Android** | `KeyGenParameterSpec` + `AndroidKeyStore`，`PURPOSE_SIGN`，`setCertificateSubject()` 自签 | **无需任何新依赖**。私钥落在 TEE/StrongBox 里**不可导出**——就算 App 数据被拖走也拿不到身份。通过自定义 `X509KeyManager` 接进 `SSLContext` |
| **Linux** | 直接调 OpenSSL（Qt 已经链了）生成 EC P-256 自签证书，写到 `$XDG_CONFIG_HOME/afmu/identity.pem`，权限 `0600` | Qt 没有证书生成 API，这段要写 ~80 行 OpenSSL。**不要**在配置 JSON 里存私钥 |

参数统一：**EC P-256**（不是 RSA——生成快、握手包小、Android KeyStore 原生支持），
有效期 20 年（钉扎之后有效期本来就没有意义，只是别让 TLS 栈以过期为由拒绝）。

两端共通的两条规矩：

- **生成是一次性的。** 换了密钥就等于换了设备，所有已配对关系全部作废。
  所以身份**存在但读不出来**时必须**报错**，绝不能当成"重新生成一个"的理由——
  静默换钥匙的表现是"所有已配对设备突然都连不上了"，而且没人查得出原因。
- **subject 只是占位**（`CN=AFMU device`）。钉的是公钥，名字放什么都不影响安全性；
  放设备名反而会把它印进配对表和日志。

#### 实现状态

第 1 步两端都已落地并交叉验证过（§12）：

| | 现状 |
|---|---|
| Linux | `src/Identity.{h,cpp}`，OpenSSL 3.x EVP API；`afmu --fingerprint` 打印指纹并给出复核命令 |
| Android | `core/Identity.kt`，AndroidKeyStore，优先 StrongBox → TEE → 软件密钥，实际归属由 `KeyInfo` 查询而非记生成时的选择 |
| base32 | 抽成不依赖 Android 的 `core/Base32.kt`，JVM 单元测试用**取自 C++ 实现的真实向量**校验两端一致 |

Linux 侧实测确认：指纹与 `openssl` 独立算出的一致；对照组
（整张证书的哈希）是完全不同的值——即钉的确实是 SPKI；
文件权限 `0600`；重启幂等；文件损坏时报错而非重新生成。

Android 侧的 KeyStore 部分**尚未在真机上跑过**（headless 环境没有 AndroidKeyStore），
装到设备上之后请用同一条 `openssl` 命令复核一次导出的证书。

## 4. 配对：指纹如何带外交换

这是整个 v2 唯一真正需要用户参与的地方，也是 MITM 的唯一窗口。
**两条路，强度不同，必须让用户知道差别。**

### 4.1 扫码配对（强 —— 推荐路径）

二维码里直接带完整指纹。带外通道（摄像头看屏幕）不经过网络，MITM 无从下手。

```
afmu://pair?v=2&host=192.168.1.30&hosts=192.168.1.30,10.42.0.1&port=8765
  &fp=K7M2Q9XFHTB4NRW2PLDS8VCGYM3JKA7QZE
  &name=ice-desktop&os=linux
```

| 参数 | v1 | v2 | 说明 |
|---|---|---|---|
| `v` | 1 | **2** | v2 客户端见到 `v=1` 要走 §8 的降级流程 |
| `fp` | — | **必填** | 展示方的 SPKI 指纹，base32 |
| `token` | 必填 | **移除** | 身份由证书承担，不再需要把长期密码印在二维码上 |

扫描方拿到 `fp` 之后：钉住它 → 逐个地址建 TLS 连接 → **握手时对端证书的
SPKI 指纹必须等于 `fp`，不等就断开并报"这不是你扫的那台设备"**，绝不放行。

> v1 的二维码里是明文 token，截图/转发/投屏等于交出访问权。
> v2 的二维码里只有公钥指纹，**泄露它不会造成任何损失**——它本来就是公开信息。
> 这是 v2 顺手解决的一个真问题。

### 4.2 授权连接（较弱 —— 无二维码时的路径）

v1 的 `/api/authorize` 流程保留，但确认码的含义变了。

v1 里 4 位确认码由请求方随便生成，只能防"我点的到底是不是这一下"，
**对 MITM 毫无作用**——中间人可以把自己的码转发过去。

v2 改成 **SAS（短认证串）**，两端各自算出同一个 8 字符串，用户比对。

#### 4.2.1 为什么不能只哈希两个指纹

最直觉的做法是：

```
sas = base32( SHA-256( min(fp_a, fp_b) || max(fp_a, fp_b) ) )[0:8]   ← 不安全，不要用
```

它**挡不住中间人**，原因是这里的攻击不是原像而是**碰撞**：

中间人 M 对 A 出示证书 M1、对 B 出示 M2。于是
A 算的是 `f(M1) = SAS(fp_A, fp_M1)`，B 算的是 `g(M2) = SAS(fp_M2, fp_B)`。
M 不需要撞上某个指定值，他只要找到**任意一对** `(M1, M2)` 使 `f(M1) == g(M2)`。
这是生日攻击：各生成约 2²⁰ 个候选密钥对、分别求值、找碰撞，
期望命中一次。**2²⁰ ≈ 100 万次 P-256 密钥生成，单核一两分钟。**

更糟的是它可以**离线**做完。`fp_A`、`fp_B` 是长期公开身份，M 事先扮演一次
客户端／服务端就能探到，然后慢慢磨出 M1/M2，攻击当场零延迟。

> 把 SAS 加长到 12–16 字符能把成本抬到 2³⁰–2⁴⁰，但那是在用 UX 换安全边际，
> 而且方向是错的——真正该做的是让离线预计算失效。

#### 4.2.2 采用的方案：commit-reveal 绑定会话随机数

标准解法是把一对**会话唯一的随机数**拌进 SAS，并用"先承诺后揭示"保证
谁都无法在看到对方随机数之后再挑自己的。这是 ZRTP 和 Signal 安全号码的成熟做法。

发起方为 A（客户端），接收方为 B（服务端）。全程在已建立的 TLS 之内：

```
1. A → B:  commit = SHA-256(n_a)        n_a 是 32 字节 CSPRNG 随机数，此时不公开
2. B → A:  n_b                          B 的 32 字节随机数，明文
3. A → B:  n_a                          揭示；B 必须校验 SHA-256(n_a) == commit，不等立即断开
4. 两端各自计算并显示：

   sas = base32( SHA-256( "AFMU-SAS-v2" || min(fp_a,fp_b) || max(fp_a,fp_b) || n_a || n_b ) )[0:8]
   显示成 XXXX-XXXX
```

- 第 1 步的 commit 是关键：B 在选 `n_b` 时看不到 `n_a`，A 在提交 `n_a` 时看不到 `n_b`。
  谁都无法针对对方的取值去搜碰撞。
- 于是 M 的 2²⁰ 次搜索**必须在线、实时、针对这一次会话完成**——而用户几秒之内就比对完了。
  离线预计算彻底作废，8 个字符（40 bit）足够。
- `min`/`max` 排序保证两端算出同一个值，与谁是客户端无关。
- 域分隔串 `"AFMU-SAS-v2"` 是 ASCII，不含结尾 NUL；将来换算法就换这个串。
- 三个消息里任何一步失败（校验不过、超时、字段缺失）→ 立即断开并**丢弃**该次配对，
  不给"再试一次"按钮复用同一组随机数。

> **为什么不用 TLS keying material exporter（RFC 5705）？**
> 密码学上它更干净——exporter 天然是会话唯一的，一步到位。
> 但 **Qt 完全没有暴露 exporter API**，Android 侧要走 Conscrypt 的非公开接口。
> 两端都拿不到的东西不能写进规范。commit-reveal 只花两个 round-trip，全用得上现成积木。

#### 4.2.3 `POST /api/pair-v2` — 线格式

TLS 已建立但双方都还没钉扎（见 §4.2.4）。请求体和响应体都是 JSON，
`Content-Type: application/json`。**这是此状态下唯一可访问的路由。**

**第 1 步 `{"step":"commit"}`**

| 字段 | 说明 |
|---|---|
| `step` | `"commit"` |
| `commit` | `SHA-256(n_a)` 的小写 hex，64 字符 |
| `name` / `os` | 请求方设备名与系统，供 B 的弹窗显示。按 v1 §3.8 的规矩过滤控制字符并截断 |

响应：

```json
{"ok": true, "session": "<32 位 hex>", "nb": "<64 位 hex>", "expires": 60}
```

`session` 是 B 生成的一次性 id，后续两步凭它认人；和 v1 的 `request` id 一样，
**只发给请求方，不写日志**。

**第 2 步 `{"step":"reveal"}`**

| 字段 | 说明 |
|---|---|
| `step` | `"reveal"` |
| `session` | 上一步拿到的 id |
| `na` | `n_a` 的小写 hex，64 字符 |

B 校验 `SHA-256(na) == commit`，不等 → `400` 并作废该 session。
通过则两端都能算出 SAS，B 弹窗显示，响应：

```json
{"ok": true, "sas": "K7M2-Q9XF", "expires": 60}
```

> 响应里回带 `sas` 只是让 A 能**自检**双方算出的值一致（防实现 bug）。
> A **必须**自己独立算一遍并显示自己算的那个，**绝不能**显示服务端回的值——
> 否则中间人只要回一个和 A 期望一致的串就骗过去了，整套机制归零。
> 不一致 → 立即断开并报"实现不匹配"，不要显示任何码。

**第 3 步 `GET /api/pair-v2?session=<id>`** — 轮询用户决定

```json
{"ok": true, "status": "pending"}
{"ok": true, "status": "granted", "name": "Pixel 8", "port": 8765}
{"ok": true, "status": "denied"}
{"ok": true, "status": "expired"}
```

`granted` 之后两端各自把对端指纹写进配对表（§4.3）。**响应里没有 token**——
v2 的身份就是那对密钥，没有东西需要交出去。

滥用防护沿用 v1 §3.8 那一套，一条不少：同一时刻只保留一个待决 session（新的回 `429`）、
拒绝后按来源 IP 冷却 60 秒、60 秒超时按拒绝处理、可以整个关掉、服务停止时清空。

#### 4.2.4 与 TLS 的关系

**这三步握手跑在 TLS 之内**：先完成 TLS（双方都还没钉扎，按 §5 的方式取对端 SPKI 指纹
但不做匹配），走完 commit-reveal、用户点"允许"之后，才把对端指纹写进已配对列表。
在此之前，连接除了 `/api/pair-v2` 之外**不得访问任何接口**，包括 `/api/info`。

UI 上的代价：用户要比对 8 个字符而不是 4 个数字。只在没有二维码时才走这条路。

### 4.3 已配对之后

指纹存进配对表；此后每次连接都必须匹配，**不匹配一律拒绝，不给"仍然继续"按钮**。
换手机/重装要重新配对——这是钉扎的本意，不是缺陷。

配对表（Linux 侧 `~/.config/afmu/peers.json`，权限 `0600`；Android 侧 SharedPreferences 的 `peersV2` 键）：

```json
[{"fp":"K7M2Q…","name":"Pixel 8","os":"android","lastHost":"192.168.1.42","lastPort":8765,
  "pairedAt":1786000000,"pinned":true}]
```

字段语义，两端必须一致：

| 字段 | 语义 |
|---|---|
| `fp` | **身份本身**。52 字符 base32，进表前一律规范化（见下）。所有查找、去重、钉扎只看它 |
| `name` / `os` | 只为了让用户认出这是哪台设备，可以随时被对端改掉，不参与任何判定 |
| `lastHost` / `lastPort` | **只是重连提示**（§13 问题 3）。多网卡的 PC 换个 IP 是常事，指纹没变就还是同一台机器 |
| `pairedAt` | 首次配对的 Unix 秒。重连**不刷新**它 —— 用户想知道的是"什么时候认识的" |
| `pinned` | 只走 v2，握不上就是失败（§8.1 第 1 条）。由"首次 v2 连接成功"置位，普通更新不得清除 |

**指纹进表前必须规范化。** 52 个 base32 字符是 260 bit 而指纹只有 256 bit，
末字符低 4 bit 是填充位；手抄或者另一个实现可能把它们填成非零，
于是同一个指纹有 16 种写法。解码再编码一遍就都收敛。
不这么做的后果不是不整洁 —— 是表里出现两条指向同一台设备的记录，
**用户删掉一条，另一条还开着门**。

同理，解不出 32 字节的指纹一律**丢弃而不是将就存下**：
存进去的话将来永远匹配不上，症状是"明明配过了却连不上"。丢掉了要在界面上说出来，
否则用户看到的只是"怎么少了一台"。

有意不做的两件事（§13 问题 2）：不限条数，不自动过期。

#### 实现状态

第 2 步两端都已落地（§12），但**还没有任何代码往里写**——写入要等第 3–6 步的
握手接上。先做"看和删"是有意的：在 v2 里表里的一条就是一道开着的门，
**能开之前先得能关**。

| | 现状 |
|---|---|
| Linux | `src/PeerStore.{h,cpp}`，`QAbstractListModel`，落盘 `peers.json`(0600)；设置页可查看、复制指纹、解除配对 |
| Android | `core/Peers.kt`（纯编解码，不依赖 Android）+ `core/PeerStore.kt`（SharedPreferences）；主界面同样可查看和解除 |
| 测试 | Linux `tests/peerstore_test.cpp`（`-DAFMU_TESTS=ON`）、Android `PeerCodecTest`，两边断言刻意一一对应 |

读写都走"读不出来就绝不覆盖"的规矩（Linux 侧抽成 `src/JsonFile.{h,cpp}`，
和 `config.json` 共用）：丢配对关系和丢 token 一样糟 ——
所有设备要重新配对，而用户完全不知道为什么。

## 5. 传输层

| 项 | 要求 |
|---|---|
| 最低版本 | **TLS 1.3**。不接受 1.2 及以下（1.2 不加密证书消息，泄露身份） |
| 套件 | 交给 TLS 栈默认（1.3 的套件集本来就都是 AEAD） |
| 客户端证书 | **必需**。服务端 `VerifyPeer`，双向认证 |
| 证书校验 | 两端都**关掉 CA 链校验**，改为手工比对 SPKI 指纹（自签证书没有 CA 可言）。各端的正确写法见下 |
| SNI | 不发送，或固定发一个常量。别把设备名放进 SNI——那是明文的 |
| ALPN | `afmu/2`，让不匹配的客户端早点失败 |

握手成功 = 双方都持有已钉扎的私钥 = **认证完成**。
未配对的设备连 TLS 都握不上，`/api/*` 整个接口面对陌生人根本不存在。
这比"每个请求检查 token"强一个量级。

### 5.1 "关掉 CA 校验 + 手工钉扎"各端怎么写

这一步最容易写成"看起来能跑但实际没在校验"，两端的正确姿势不一样：

| 端 | 正确写法 | 常见的错误写法 |
|---|---|---|
| **Qt** | `setPeerVerifyMode(QSslSocket::QueryPeer)`，在 `encrypted()` 信号里取 `peerCertificate()` 算 SPKI 指纹并比对，不匹配立刻 `abort()` | ❌ `VerifyNone` + 在 `sslErrors` 里比对。**`VerifyNone` 下 `sslErrors` 不保证触发**，钉扎代码可能一次都不执行 |
| **Android** | 自定义 `X509TrustManager`，在 `checkServerTrusted` / `checkClientTrusted` 里比对 SPKI，不匹配 `throw CertificateException` | ❌ 空实现的 TrustManager + 握手后再检查。握手已经完成，数据可能已经发出去了 |

两端共同的要求：**校验失败必须是异常/断连，不能是一个被忽略的返回值。**

指纹算的是 `SHA-256(DER(SubjectPublicKeyInfo))`（§3.1）——注意是 SPKI 那一层封装，
不是裸公钥点，也不是整张证书。两端实现完之后务必按 §12 的第 1.5 步交叉验证一次。

时序：

```
客户端                                          服务端
 |-- TCP connect ------------------------------→ |
 |-- TLS 1.3 ClientHello (ALPN afmu/2) --------→ |
 |← ServerHello + {加密的} Certificate ---------|
 |   校验 SPKI 指纹 ∈ 已配对表，否则断开          |
 |-- {加密的} Certificate + Finished ----------→ |
 |                校验客户端 SPKI 指纹，否则断开   |
 |========== 之后全部是 v1 的 HTTP 报文 =========|
 |-- GET /api/list?path=/home/ice -------------→ |
 |← 200 {"entries":[…]} -----------------------|
```

**v1 的 HTTP 层一个字都不用改。** v2 只是在下面垫了一层 TLS，
`/api/list`、`/api/upload`、Range 续传、multipart 全部照旧。
这是选 TLS 而不是自定义帧格式的另一个好处：上层代码零改动。

### 5.2 认证的边界

**握手成功 + 对端指纹在配对表里 = 认证完成**，v2 连接上不再检查 token。

这不是省事，是把认证从"每个请求带一个长期共享密钥"换成"对端持有一把被钉扎的私钥"。
留着 token 只会把 v1 的弱点原样搬进 v2（§13 问题 4 已就此拍板）。

反过来说，两个条件缺一不可：

- **只有握手成功不算数。** `QueryPeer` 下客户端不交证书，握手照样成功——
  判空是挡住匿名连接的唯一一道，漏掉它等于把 mTLS 写成了单向 TLS。
- **只有指纹对不上也不算数。** 表里没有就是没有，不给"仍然继续"。

#### 实现状态（Linux 服务端，第 3 步）

没有换成 `QSslServer`：它在 accept 之后立刻开始握手，而 §8.1 第 4 条要求
**先看首字节**再决定这条连接走 TLS 还是 v1 明文。所以仍是 `QTcpServer`，
每条连接建一个 `QSslSocket`，`peek(1)` 之后再 `startServerEncryption()`。
（`peek` 不是 `read`——那个字节属于 ClientHello，读掉的话 TLS 引擎就拼不出完整握手了。）

实测确认，对着运行中的实例逐条验过：

| 场景 | 结果 |
|---|---|
| 带已配对证书连接 | TLS 1.3 握上，ALPN 协商到 `afmu/2`，`/api/info` **不带 token** 直接 200 |
| 不交客户端证书 | 握手成功但被判空，断开 |
| 交了证书但不在配对表 | 断开，日志打出对端指纹 |
| 首次 v2 连接成功 | 配对表里该条自动置 `pinned`（§8.2 第 2 阶段） |
| ALPN 不是 `afmu/2` | 握手直接失败（`BAD_EXTENSION`），够不到 HTTP 层 |
| `allowLegacyPlaintext` 关闭 + 明文连接 | **零字节响应**后断开，不回 400 也不回任何 HTTP 报文 |
| `allowLegacyPlaintext` 开启 | v1 一致性套件 65 项全过，行为没有任何变化 |

指纹与 `openssl` 独立算出的值再次交叉验证一致（这次是对端方向）。

#### 实现状态（Linux 客户端，第 4 步）

`QNetworkAccessManager` 走 https，钉扎挂在 **`QNetworkAccessManager::encrypted`** 上——
这个信号的时机正是要害：**握手刚完成、还没有发出任何用户数据**。
在这里 `abort()`，token、路径、文件内容一个字节都不会漏给冒充者。
（实测印证：指纹不匹配那一次，服务端连一条请求记录都没有。）

走不走 TLS 在 `setPeer()` 时就定死：地址在配对表里有记录就必须走 v2，
之后不存在"握手失败就退回明文"的路径（§8.1 第 1 条）。

Linux ↔ Linux 逐条实测：

| 场景 | 结果 |
|---|---|
| 双方互相配对 | 全程 TLS 1.3，双向钉扎，`/api/info` 不带 token 直接连上 |
| 客户端钉的指纹不对 | 连接中止，界面说"这不是你配对的那台设备"；**服务端没收到任何请求** |
| 已配对对端只提供明文 | 只发出一个 ClientHello 就失败，**没有第二次明文重试** |
| 对端没配对过 | 照旧走 v1 明文，服务端零条加密连接 |
| 3 MB 下载 + Range 续传 | 字节完全一致（`pumpFile` 的写入节流在 `QSslSocket` 上照常工作）|

##### 两处栽在 Qt 上的坑，都是实测出来的

**1. ALPN 不能当安全边界，因为 QNAM 根本不让你设。**

`QNetworkAccessManager` 会**覆盖**请求里设的 ALPN，自己提 `{h2, http/1.1}`。
服务端只接受 `afmu/2` 的话，第一个连不上的就是我们自己的客户端（`BAD_EXTENSION`）。
所以服务端的 ALPN 列表是 `{afmu/2, http/1.1}`，由服务端在 ALPN 阶段选中
`http/1.1`，顺带把 QNAM 默认开启的 HTTP/2 挡掉——比在客户端逐个请求关
`Http2AllowedAttribute` 可靠，后者实测会让握手直接卡死。

于是 §5 那句"让不匹配的客户端早点失败"**在 Qt 这条路上做不到**：随便一个
HTTPS 客户端都能握上手。挡住它的从来不是 ALPN 而是钉扎——没有已配对的
客户端证书，握完也进不去。ALPN 在这里只是个标记。

**2. QNAM 会因为 `sslErrors` 中止连接，`QueryPeer` 拦不住它。**

服务端那边 `QueryPeer` 确实让校验错误变成非致命的，但 QNAM 多一层自己的判断：
没有明确 `ignoreSslErrors()` 就中止（实测 `SslHandshakeFailedError`）。

所以客户端**必须**在 `sslErrors` 里放过自签证书那几种错误。
这看起来很像 §5.1 说的错误写法，区别要说清楚：

- ❌ 错的是**在 `sslErrors` 里做身份判断**——那段代码可能一次都不执行。
- ✅ 这里 `sslErrors` 里一个字节的身份判断都没有，只是告诉 Qt"CA 这条路我们本来就不走"；
  而且**只放过预期内的那几种**，多出任何一种没见过的错误就照旧中止。
  真正的比对在 `encrypted` 里，不匹配就 `abort()`。

两处和草案原文的偏差，都已按实测修正：

1. **未配对设备现在是直接断开**，而不是"放进来但只许访问 `/api/pair-v2`"。
   那个接口是第 8 步的事；在它存在之前放行等于开一个没有任何用处的口子。
   做第 8 步时要把这里改回 §4.2.4 描述的样子。
2. `allowLegacyPlaintext` **默认开着**，而 §8.1 第 2 条写的是默认关。
   那是 §8.2 第 3 阶段的事：现在客户端一侧还没做，关掉等于本机谁也连不上。

### 5.3 实现状态（Android，第 5–6 步）

| | 做法 |
|---|---|
| 服务端 | 接受的 socket 用 `SSLSocketFactory` 包一层，`wantClientAuth`，钉扎在自定义 `X509TrustManager` 里**抛异常** |
| 客户端 | `HttpsURLConnection` + 同一套 KeyManager/TrustManager，`HostnameVerifier` 恒真（名字这个问题已经被钉扎取代） |
| 密钥 | 自己写 `X509ExtendedKeyManager` 返回 KeyStore 里的私钥句柄，不走 `KeyManagerFactory`——私钥不可导出，让工厂去"取"它只会以难查的方式失败 |
| 钉扎失败 | `CertificateException`。**必须是异常**：返回值形式的拒绝会被 TLS 栈忽略，握手照常完成，"校验过了"就成了一句空话 |

#### 已在纯 JVM 上验证的（`TlsPinningTest`，8 项）

真机跑不了，但最容易错、错了又最难查的两件事不需要真机：

- **指纹算得对不对**：拿 Linux 端真实生成的一张证书当向量，期望值由 `openssl`
  独立算出。Java 的 `PublicKey.getEncoded()` 与 `i2d_X509_PUBKEY` 逐字节相同，已确认。
  对照组（整张证书的哈希）是不同的值，即钉的确实是 SPKI。
- **不认识的对端会不会被挡住**：未配对指纹抛异常、空证书链抛异常、
  `getAcceptedIssuers` 为空。

#### 一处平台限制，改了设计：**Android 端不做首字节分流**

§8.1 第 4 条的分流要"偷看首字节再把它还给 TLS 引擎"，靠的是
`SSLSocketFactory.createSocket(Socket, InputStream consumed, boolean)`——
**Android 没有这个重载**（平台保留的是 Java 8 之前的签名集，实测编译期就没有）。
偷看过的 ClientHello 字节还不回去，握手就永远完不成。

所以手机一次只提供一种协议，由设置项决定：明文 v1（默认，现有客户端都说这个）
或加密 v2。Linux 端仍然一个端口同时服务两者，因为 Qt 让它 peek。
代价只落在"手机当服务端"这个方向，而且它出现在设置项里，不是藏在某个回退分支里。

**尚未验证的**：握手本身、AndroidKeyStore 取密钥、`SSLSocketFactory` 包装已 accept 的
socket 这三件事都要真机。装到设备上之后，第一件事是用 §12 第 1 步那条 `openssl`
命令复核导出的证书。

## 6. 发现协议 v2：不再广播设备名

v1 的问题实测过：往 UDP 8766 发一个包，任何人都能拿到
`{"afmu":1,"name":"icelab","os":"linux","port":8765}`。设备名、系统、端口全泄露。

v2 分两种模式：

### 6.1 常态模式（默认）

应答里**不含设备名和系统**，只含一个滚动标识：

```json
{"afmu": 2, "port": 8765, "rid": "9f3c1a77"}
```

```
rid = SHA-256( spki_fingerprint || floor(unix_time / 300) )[0:4]  → 8 位 hex
```

- **已配对的设备**手里有对方指纹，能自己算出同样的 `rid`，于是认得出"这是我的 Pixel"。
- 时间窗跨越边界时，接收方同时接受 `t` 和 `t-1` 两个窗口，避免边界抖动。
- 依赖两端时钟大致同步（±5 分钟内），局域网场景成立。
- **取 4 字节（32 bit），不是 2 字节。** 16 bit 在多设备环境下有 1/65536 的误认率，
  而 UDP 应答不差这两个字节。

**这挡住了什么、没挡住什么**（别把它当匿名）：

| 观测者 | 结果 |
|---|---|
| 陌生人**单次**观测 | 只看到一串随机 hex，问不出设备名、系统、身份 ✅ |
| 陌生人**连续**观测多个时间窗 | rid 序列本身就是高熵指纹（3 个窗口 = 96 bit），**仍可关联为同一台设备** ⚠️ |
| 曾经在 §6.2 配对模式下见过该设备 `fp` 的观测者 | 此后**永久**能算出它每个窗口的 rid，追踪能力完整 ⚠️ |

所以准确的说法是：**在从未见过该设备 `fp` 的前提下，单次观测无法识别它是谁；
连续观测仍能把它和自己关联起来。** 要挡住连续观测得让 rid 与观测者不可预测的东西绑定，
而 UDP 广播场景里没有这样的东西——这是广播发现的固有代价，不是实现缺陷。

### 6.2 配对模式（用户显式开启，限时）

只有用户在界面上点了"允许被发现 / 开始配对"，才在 **60 秒内**应答完整信息：

```json
{"afmu": 2, "port": 8765, "name": "icelab", "os": "linux", "fp": "K7M2Q…"}
```

超时自动回到常态模式。**这样"陌生人能看到设备名"的窗口从"永远"缩短到
"用户主动开启的那一分钟"。**

> 注意：`fp` 出现在明文 UDP 里是**故意的**，它是公钥指纹，泄露它不会造成访问权损失。
> 但它是**长期不变的**标识：谁在这 60 秒里抓到了它，此后就能永久算出该设备的 `rid`
> （见 §6.1 的表格）。所以"短暂出现"限制的是被抓到的**概率**，不是被抓到之后的影响——
> 一次泄露 = 永久可追踪。这是配对便利性的实际代价，接受它，但别说成"没有代价"。

## 7. token 的去向

v2 里 **token 不再是 `/api/*` 的认证手段**——认证由 mTLS 完成。

保留 token 只为一件事：**浏览器界面**（§9）。配置项从"访问 token"改名为
"浏览器访问密码"，并且默认**不生成**，用户开启浏览器界面时才生成。

顺带解决 v1 的一个实测问题：`?token=` 允许 token 出现在 URL 里，
会落进代理日志、浏览器历史、Referer。v2 的 `/api/*` **不再接受任何 query 里的凭证**。

## 8. 与 v1 的兼容和降级防护

这一节最容易写错，写错了 v2 就白做——攻击者只要伪装成 v1 设备就能把你打回明文。

### 8.1 规则

1. **配对表里 `pinned: true` 的对端，永远只走 v2。** 对它发起的连接如果
   TLS 握手失败，就是失败，**绝不回退到明文 HTTP**。这是降级攻击的唯一防线。
2. 从没配对过的设备，允许在用户明确同意后走 v1 明文，但界面上必须
   持续显示"未加密"状态，且默认关闭（设置项：`allowLegacyPlaintext`，默认 `false`）。
3. v2 设备的发现应答是 `afmu:2`；v1 客户端会因为 `afmu != 1` 直接忽略（
   本次审查已经把两端的版本判定统一成严格相等，正好为此铺路）。
4. 端口：v2 用**同一个 8765**。服务端在 accept 后偷看第一个字节：
   `0x16` 是 TLS ClientHello，其它按 v1 明文处理（仅当 `allowLegacyPlaintext` 开启）。
   这样一个端口同时服务新旧客户端，不用占两个端口。
   **`allowLegacyPlaintext` 关闭时，非 `0x16` 首字节一律直接断开**，不要回 400、
   不要回任何 HTTP 报文——零信任模式下这个端口在效果上只听 TLS。

> **第 1 条只保护客户端，服务端侧需要第 4 条那半句才完整。**
> 首字节分流发生在 TLS 握手之前，也就是在服务端知道对面是谁之前，
> 所以服务端无法判断"这个明文连接是不是来自某个 `pinned` 对端"，
> 没法像客户端那样按对端身份拒绝回退。
> 服务端能做的只有一刀切：要么整个进程允许明文，要么完全不允许。
> 这不是漏洞（v1 路径仍然要 token），但别指望 `pinned` 标志在服务端方向上起作用。

### 8.2 升级路径

| 阶段 | Android | Linux | 用户感知 |
|---|---|---|---|
| 1 | 双栈：能收 v1 也能收 v2 | 同左 | 无 |
| 2 | 已配对设备自动升级到 v2（首次 v2 连接成功后写 `pinned:true`） | 同左 | 提示"已启用加密" |
| 3 | `allowLegacyPlaintext` 默认关 | 同左 | 老设备需手动放行 |
| 4 | 删除 v1 明文路径 | 同左 | 必须都升级 |

## 9. 浏览器界面怎么办（诚实说明）

`WebUi.kt` 那个自包含单页是 v1 的一大卖点：PC 上什么都不装就能收发。
**它无法达到 v2 的安全标准**，原因是浏览器做不了我们要的钉扎：

- 浏览器不会拿客户端证书去做 mTLS（除非用户手工装证书，UX 灾难）。
- 自签服务端证书会弹"不安全"警告，用户点"继续"就等于关掉了 MITM 防护。

结论：**浏览器界面降级为显式的"访客模式"**。

- 默认**关闭**。开启时界面上明确写"访客模式不防中间人，只在你信任的网络里用"。
- 开启后走 HTTPS（自签）+ 浏览器密码认证，至少挡住被动嗅探。
- 零信任模式（设置项 `zeroTrustMode`）打开时，访客模式**不可用**，开关置灰。

不要试图把访客模式伪装成安全的。它是个便利功能，标清楚就行。

## 10. 加密之后还剩什么泄露

| 泄露项 | 是否可见 | 能否缓解 |
|---|---|---|
| 两个 IP 之间有连接、端口 8765 | ✅ 可见 | 不能（换端口只是障眼法） |
| 传输时刻、持续时长 | ✅ 可见 | 不能 |
| 传输字节量 → 文件大小 | ✅ 可见 | 填充可缓解，代价大，**建议不做** |
| 文件名、路径、目录结构 | ❌ 不可见 | TLS 已解决 |
| 设备名、系统、身份 | ❌ 不可见 | TLS 1.3 加密证书 + §6 滚动 rid |
| token / 凭证 | ❌ 不可见 | 已不在传输中 |
| "这是 AFMU 协议" | ⚠️ 可推断 | ALPN 明文含 `afmu/2`；在意的话可去掉 ALPN，代价是失败诊断变差 |

最后一行值得单独说：如果你的威胁模型里"被发现在用这个工具"本身就是问题，
那要做的是流量混淆，那是另一个量级的工程，不建议在局域网工具里做。

## 11. 不依赖 v2、现在就能做的收敛

v2 是大工程。下面这些**不改协议、不破兼容**，可以立刻落地，
把 v1 在半可信网络（比如公司内网）下的暴露面压下去：

| # | 改动 | 收益 | 工作量 |
|---|---|---|---|
| A1 | `/api/*` 不再接受 `?token=`；浏览器下载改用**短时下载券**（见下） | token 不再进日志/历史/Referer | 小 |
| A2 | 发现应答默认不含 `name`/`os`，改为用户开启"配对模式"时才带 | 关掉最直接的元数据泄露，且是 §6 的前置工作 | 小 |
| A3 | `/api/authorize` 按来源 IP 限速 + 全局冷却，拒绝后延长封禁 | 挡住弹窗骚扰和换 ID 刷屏 | 小 |
| A4 | token 校验失败计数：同一 IP 连续失败 N 次后指数退避 | 实测 200 次错误尝试 0.78 秒无任何惩罚；补上纵深 | 小 |
| A5 | `Host` 头白名单（只认本机 LAN 地址 / `.local`），并对浏览器界面加 `Origin` 校验 | 挡 DNS-rebinding 和跨站请求 | 小 |
| A6 | 界面上把"未加密"状态常驻显示，别只写在文档里 | 用户知情 | 很小 |

### 11.1 A1 的短时下载券

浏览器的 `<a href>` 没法带自定义头，这是 `?token=` 当初存在的唯一理由。
替代物要定义清楚才能实现，三个点都得说死：

```
GET /api/download?path=…&ticket=<exp>.<mac>

exp = 过期的 Unix 秒（十进制）
mac = base64url( HMAC-SHA256( token, "afmu-dl-v1\n" || exp || "\n" || path ) )[0:22]
```

- **防伪造**：MAC 用本机 token 当密钥，服务端**无状态**校验，不用记任何东西。
  域分隔前缀防止这个 MAC 将来被别的用途复用。券绑定 `path`，换个路径就失效。
- **过期语义**：`exp` 约束的是"**开始**下载"，不是整个传输。
  服务端在决定响应之前校验一次 `now <= exp`，一旦开始写响应体就不再看——
  否则 5 秒过期等于禁止下载任何大于几十 MB 的文件。签发时给 `exp = now + 5` 就够，
  用户点链接是立刻发生的事。
- **不叫"一次性"**。真一次性要服务端记已用 nonce，和上面的无状态校验直接矛盾。
  二选一，这里选无状态：券在 5 秒窗口内可重放，但它只能重放**同一个路径的下载**，
  且窗口短到没有实际转发价值。想要真一次性就得接受一张服务端状态表，不值得。

发券的地方是浏览器界面自己（已经过了密码认证），页面上的每个下载链接现拼现用。

**建议顺序：先做 A1–A6（一两天），再评估 v2 要不要上。**
A 组做完之后，v1 在公司内网这种"半可信"环境下就基本够用了；
v2 是为咖啡厅 Wi-Fi 那种真正的零信任场景准备的。

## 12. 实施清单（v2）

按依赖顺序，每项都可独立提交：

1. **身份层**：两端生成/持久化 EC P-256 密钥与自签证书；实现 SPKI 指纹计算与 base32 展示。

   **做完立刻交叉验证指纹，别等到第 3 步。** 两端各打印一次自己算出的指纹，
   再用外部工具独立算一遍，三个值必须完全相同：

   ```
   openssl x509 -in cert.pem -pubkey -noout \
     | openssl pkey -pubin -outform DER \
     | sha256sum
   ```

   mTLS 手工钉扎最常见的翻车就是两边对"SPKI"的理解差一层封装
   （有人哈希了整张证书，有人哈希了裸 EC 点）。握手层调通之后再发现这个，
   现象是"证书明明对却一直不匹配"，非常难查。这一步 10 分钟，省半天。

2. **配对表**：`peers.json` / SharedPreferences 结构，增删查改 + 界面。**（已完成，见 §4.3「实现状态」）**
3. **Linux 服务端**：首字节分流 + `QSslSocket` 手工升级，`QueryPeer` + 手工指纹比对。
   **（已完成，见 §5.2「实现状态」——没用 `QSslServer`，原因在那里）**
4. **Linux 客户端**：`QNetworkAccessManager` 走 https，钉扎挂在 `encrypted` 上
   （**不是** `sslErrors`，原因见 §5.2）。**（已完成）**
5. **Android 服务端**：包装已 accept 的 socket + AndroidKeyStore 的 `X509KeyManager` + 自定义 `X509TrustManager`。
   **（代码完成，待真机验证；见 §5.3——没用 `SSLServerSocket`，也不做首字节分流，原因在那里）**
6. **Android 客户端**：`HttpsURLConnection` 挂同一套 TrustManager/KeyManager。
   **（代码完成，待真机验证）**
7. **二维码 v2**：`fp` 参数，`token` 移除，`v=2`。
8. **SAS 授权流程**：`/api/pair-v2` 三步 commit-reveal（§4.2.3）、8 字符 SAS 计算与两端 UI。
   注意 A 端必须显示**自己算的** SAS，不是服务端回的那个。
9. **发现 v2**：滚动 `rid` + 配对模式。
10. **降级防护**：`pinned` 标志、首字节嗅探分流、`allowLegacyPlaintext` 开关。
11. **访客模式**：浏览器界面开关 + HTTPS + 警示文案。
12. 文档：把本草案扶正为 `PROTOCOL.md` 的 v2 章节。

其中 1–6 是主干，做完就已经具备完整的抗 MITM 能力；7–11 是把配对体验和
元数据泄露补齐；12 收尾。

## 13. 待定问题

写实现之前需要拍板的：

1. **Android 私钥要不要强制 StrongBox？** 强制的话老设备可能没有，
   要准备 fallback 到 TEE。建议：优先 StrongBox，失败降级 TEE，都不行才用软件密钥并提示。
2. **配对表满了怎么办？** 建议不限条数但提供界面删除；不做自动过期
   （自动删掉一台你半年没用的设备，下次用要重新配对，很烦）。
3. **多网卡 PC 换 IP 之后怎么重连？** 指纹不变，靠发现协议的 `rid` 认出来即可。
   `lastHost` 降级为提示，不再是身份的一部分。
4. **要不要保留 token 作为第二因子？** —— **已拍板：不要。**
   mTLS 已经足够，多一个长期共享密钥就多一个泄露面，而且 UX 直接回到 v1。

   真正想要"就算私钥被偷也还有一道"的话，正确解法不是加共享密钥，而是**给密钥本身加锁**：
   Android 侧在 `KeyGenParameterSpec` 上加 `setUserAuthenticationRequired(true)`
   配合 `setUserAuthenticationParameters(300, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`，
   于是签名操作需要指纹/PIN，5 分钟内免重复解锁。
   这比第二因子强——密钥在 TEE 里且用不了，不是"被偷了但还有一道"——
   而且日常 UX 几乎无感。Linux 侧没有等价物（`identity.pem` 就在盘上），
   要对等的话得接 系统 keyring，属于 v2 之后的事。
